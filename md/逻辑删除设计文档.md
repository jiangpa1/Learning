# 逻辑删除设计文档

> 项目：Learning（Spring Boot 2.7.18 + MyBatis-Plus 3.5.5 + MySQL 8 + Redis）
> 目标：`tb_user` / `tb_article` / `tb_category` / `tb_comment` 四张表统一逻辑删除
> 日期：2026-09-18
> 前置阅读：`md/文章模块接口文档.md`（四张表建表 SQL）、`md/分类与评论模块接口文档.md`（`uk_name` 唯一索引）

---

## 一、结论先行

1. **改动只有三处**：四张表加 `deleted TINYINT NOT NULL DEFAULT 0`、四个实体加 `@TableLogic`、`ArticleServiceImpl.deleteArticle` 补清一个 Redis key。
2. **Service 层代码一行都不用改** —— 这是 `@TableLogic` 最大的价值。
3. **但有两个地方会「静默变坏」**，必须处理：
   - **唯一索引与逻辑删除冲突**（`tb_user.username`、`tb_category.name`）→ 同名永远无法复用，且报错文案是笼统的"数据已存在！"
   - **Redis 里文章的浏览量 key 会永久残留**（`views` key 不设 TTL，删文章不清就永远删不掉）
4. 第三节的**方案选择是本次唯一的架构决策**，不选就没有稳定的行为契约。

## 二、`@TableLogic` 到底改写了什么

MyBatis-Plus 在**执行器层面**拦下 SQL 加工，所以只对**走 MP 发起的操作**生效。

### 2.1 四条自动改写规则

| 你的代码 | 实际执行的 SQL | 说明 |
| --- | --- | --- |
| `selectById(id)` | `SELECT ... WHERE id=? AND deleted=0` | 查不到已删除行 |
| `selectList(wrapper)` / `exists(wrapper)` / `selectCount(wrapper)` | `... WHERE deleted=0 AND (你的条件)` | **每个查询都会自动拼** |
| `deleteById(id)` | `UPDATE tb_x SET deleted=1 WHERE id=? AND deleted=0` | **不再是 DELETE** |
| `updateById(entity)` | `UPDATE ... WHERE id=? AND deleted=0` | 已删除的行改不动 |

### 2.2 三个「不生效」的边界（⭐ 面试和翻车都在这）

| 边界 | 后果 |
| --- | --- |
| **`@Select` / XML 里的手写 SQL** | 完全绕过，**必须自己写 `AND deleted=0`**。这是 `@TableLogic` 最容易翻车的地方 |
| **在 `wrapper` 里再手写 `.eq(Xxx::getDeleted, 0)`** | 会拼成 `deleted=0 AND deleted=0`，不报错但没意义。**完全交给注解，业务代码不感知 `deleted` 字段** |
| **`deleted` 用包装类型 `Integer`（本项目）** | 老数据若为 `NULL`，`deleted=0` 不成立 → **该行被当作已删除，查不出来**。所以建表必须 `NOT NULL DEFAULT 0` |

### 2.3 配置项：本项目的选择

MP 默认值就是 `logic-delete-value: 1` / `logic-not-delete-value: 0`，**所以 `application-local.yml` 里什么都不用配**。

> 建议**不配**：配置里出现 `deleted` 容易和实体里的字段名混淆，也无助于可读性。默认值即约定，靠本文档和实体注解说明。

### 2.4 `deleted` 的默认值为什么必须是 0

写 `DEFAULT 1` 的话，表里**所有历史数据**会立刻被判定为"已删除"，接口全返 404 —— 看起来像数据全丢了（改回 `0` 即可恢复，不用找回数据）。

## 三、⭐ 唯一索引与逻辑删除的冲突（本次核心）

### 3.1 冲突的成因：应用层查重和数据库唯一约束看的不是同一个集合

**现状**（`CategoryServiceImpl`）：

```java
// addCategory：应用层查重
boolean exists = categoryMapper.exists(
        new LambdaQueryWrapper<Category>().eq(Category::getName, categoryDTO.getName()));
if (exists) throw new BusinessException("分类名已存在");
```

加了 `@TableLogic` 之后，`exists()` 会被自动拼成 `... WHERE deleted=0 AND name=?`：

| | 覆盖范围 | 结果 |
| --- | --- | --- |
| **应用层查重** | 只查 `deleted=0` | 已删除的同名分类**看不见** → 查重通过 ✅ |
| **数据库 `uk_name`** | 查**全部行**（含 `deleted=1`） | 插入时撞唯一键 → `DuplicateKeyException` ❌ |

**于是只要删除过一个"后端开发"分类，以后永远无法再建同名分类**，而用户根本看不到那个被删的分类 —— 他眼里"这名字明明没人用"。

> **一句话总结**：唯一索引不知道什么是逻辑删除，它只管物理行。删掉的分类物理行还在，索引照样拦。

**用户模块同理**：`tb_user.username` 有唯一索引。删掉用户 `zhangsan` 后，他**再也注册不回来**，且提示是 `GlobalExceptionHandler` 兜底的"数据已存在！"（笼统文案，用户完全不知道发生了什么）。

### 3.2 四个方案

| 方案 | 做法 | 优点 | 代价 | 适合 |
| --- | --- | --- | --- | --- |
| **A 删除时改名** | 逻辑删除前把 `username` 改成 `zhangsan_del_{id}`，同时清空 email 等唯一字段 | 保留 `deleted` 单列唯一索引，能无限次删建 | 数据被改写，`_del_` 后缀进日志/审计；需要额外一次 `UPDATE`，且要考虑该 `UPDATE` 本身失败的回滚 | 想"名字可复用"且不愿加字段 |
| **B 唯一索引带 `deleted`** | `UNIQUE(username, deleted)` | 索引改动最小 | ❌ **只能删一次** —— 同名删第二条会撞键（两条 `(name, 1)` 重复）。面试官一问"删两次呢"就答不上 | ❌ 不建议 |
| **C 索引带删除时间戳** | 加 `delete_time BIGINT NOT NULL DEFAULT 0`，`UNIQUE(username, delete_time)`；未删除时恒为 0，删除时写入毫秒时间戳 | 无限次删建 + 可审计何时删的 | 多一个字段和一处赋值逻辑，复杂 | 生产环境标准做法 |
| **D 明确接受限制** | 不改索引，明确"用户名/分类名不可复用"写进接口文档 + 测试用例；把 `DuplicateKeyException` 的兜底文案改得能指向原因 | 零风险、零改动、契约最清晰 | 用户无法复用名字（产品上通常可接受：用户名唯一是常态） | ⭐ 本项目推荐 |

**选型理由（本项目选 D）**：

1. 用户名"不可复用"是**绝大多数真实产品的行为**（GitHub、微博都不允许抢注已注销用户名），业务上不构成缺陷；
2. 分类名重复创建的需求本身很低频，用户换个名字即可；
3. 换来的是"唯一索引 = 权威约束"这层语义**保持干净** —— 不引入 `_del_` 这种污染数据的写法，也不需要额外的 `delete_time` 字段和维护逻辑；
4. **代价可被准确地告知**：把笼统的"数据已存在！"改成能指向原因的文案，用户体验上的坑就填上了。

> 若以后要做"注销后 90 天释放用户名"，再升级到方案 C —— 那才是 C 真正值得的场景（需要知道"什么时候删的"来决定是否释放）。

### 3.3 选中方案（D）后必须同步的三处

1. **`GlobalExceptionHandler` 的 `DuplicateKeyException` 文案**：现在是硬编码 `"数据已存在！"`（`Result.paramError`），分类和用户共用同一个处理器 → 分类重名时回一句跟用户有关的话，或者笼统到没信息量。**改成能指向原因的中性文案**，或按 `e.getMessage()` 里的索引名 `contains` 区分（`uk_name` / `username`）。
2. **接口文档补一句**：「已删除的用户名/分类名不可再次使用」，并说明原因（唯一索引覆盖全部物理行）。
3. **测试用例补两条**：删了再建同名 → 期望 400 + 可理解的提示（不是 500、不是笼统文案）。

## 四、连带影响（逐项回归清单）

逻辑删除不是"加个注解就完事"，下面每一条都可能被改坏。

| # | 位置 | 原来的行为 | 逻辑删除后 | 要做什么 |
| --- | --- | --- | --- | --- |
| 1 | `CategoryServiceImpl.deleteCategory` | `selectCount(article where category_id=?)` 统计篇数 | MP 自动加 `deleted=0` → **只算有效文章**（这正是想要的） | 无需改代码，但**提示语口径变了**，要确认"该分类下还有 N 篇文章"里的 N 语义 |
| 2 | `CategoryServiceImpl.addCategory` / `updateCategory` | 查重靠 MP 查询 | 查重看不见已删除分类，**权威判断落到唯一索引** | 见第三节 |
| 3 | `CommentServiceImpl.addComment` | 校验文章存在（`selectById`） | 已删文章 → 自动返 null → "文章不存在" ✅ | 验收确认即可 |
| 4 | **评论的级联** | 无 | 文章逻辑删除后，**它的评论仍在表里且接口可查**（评论本身没删） | ⭐ **设计决策**：是否级联逻辑删除评论？不级联 = 数据留着（回收站思路）；级联 = 删文章要额外 `UPDATE tb_comment`，且要考虑失败回滚。建议**记下取舍、暂不级联** |
| 5 | `ArticleServiceImpl.updateArticle` / `deleteArticle` | 先 `selectById` 判存在 → 再判归属 | 已删文章 `selectById` 返 null → 抛 404「文章不存在」 | 无需改代码，符合预期 |
| 6 | **`ArticleServiceImpl.deleteArticle` 的缓存清理** | 清 `articleDetail(id)` 和 `articleViews(id)` | 同样清，**但 `articleLock(id)` 没清** | ⭐ **补上 `CacheKeys.articleLock(id)`**：锁有 10 秒 TTL，影响小，但顺手清更干净 |
| 7 | **Redis 的 `views` key 永久残留** | 删文章时清了 `views` | 逻辑删除下 ID **不会被复用**（自增），所以残留 key 永远不会被读到 → **永久垃圾** | 已在第 6 条里清理，**但要意识到严重性**：`views` key 不设 TTL，不清就是永久堆积 |
| 8 | `User` 删除 | 物理删 | 用户逻辑删除后，他的文章仍在、列表仍返回，但 `selectBatchIds` 查不到他 → 昵称兜底成 `"未知作者"` | 预期行为，但要知道现象（脏数据 vs 已注销，文案分不清是已知瑕疵） |
| 9 | 全局 | — | **所有 Wrapper 查询自动带 `deleted=0`** | 以后写统计/报表类 SQL 要记得：默认排除已删除，不一定是你要的 |

## 五、Redis 与逻辑删除的交叉点（本项目特有）

缓存和逻辑删除的交集只有一处，但很容易漏：

```
DELETE /article/{id}
  → articleMapper.deleteById(id)            → UPDATE tb_article SET deleted=1 ...
  → cacheEvict(detail) + cacheEvict(views)  ← 已有
  → 【要补】cacheEvict(lock)
```

**为什么 `detail` 必须清**：否则命中缓存的请求会拿到"已删除文章"的完整内容 —— 逻辑删除在缓存层被绕过，用户能继续读到已删文章。**这是逻辑删除 + 缓存的经典翻车点**。

**为什么 `views` 必须清**：`views` key 不设 TTL（设计所需，见 `Redis缓存设计文档.md` 第 12 条）。文章 ID 自增不复用 → 这个 key 从此再也不会被访问，**永久占着内存**。删文章不清，Redis 里就会累积所有已删除文章的浏览量 key。

## 六、验收清单

### 6.1 逻辑删除本身

```
① 删一个用户/文章/分类/评论 → 接口返 200
② SELECT * FROM tb_user WHERE id=?          → 物理行【还在】，deleted=1
③ GET /user/{id}                           → 404
④ 对应列表接口                              → 该记录不再出现
⑤ 再次删除同一个 id                          → 仍返 200（MP 的 UPDATE 带 deleted=0，影响 0 行不报错）
⑥ 尝试更新已删除的记录                        → 404 / 改不动
```

**第 ②③ 步必须成对看**：只测接口会以为"数据没了"，只查库会以为"没删掉"。**"库里在、接口看不到"才是逻辑删除的正确形态。**

### 6.2 唯一索引冲突（第三节的结论落地）

```
① 注册用户 aa11 → 删除 aa11 → 再注册 aa11
     期望：按选定方案 —— 方案 D 下返 400 +【可理解的提示】，不是 500、不是笼统"数据已存在！"
② 建分类"后端开发" → 删除它 → 再建"后端开发"
     期望：同上（走数据库唯一索引分支，不是应用层查重分支）
③ 确认【应用层查重分支】和【DB 唯一索引分支】分别怎么触发
     - 应用层：库里存在 deleted=0 的同名 → BusinessException("分类名已存在")
     - DB 层：库里只有 deleted=1 的同名 → DuplicateKeyException → 兜底文案
```

### 6.3 连带影响

```
① 删掉某分类下【最后一篇】文章 → 再删该分类      期望：能删成功（计数已排除已删文章）
② 删掉某分类下的【部分】文章 → 删该分类          期望：提示"还有 N 篇"，N 只算有效文章
③ 删掉一篇文章 → GET /comment/list?articleId={id} 期望：评论仍在（若未级联）
④ 删掉一篇文章 → 立刻 GET /article/{id}           期望：404（不是缓存里的旧内容）★
⑤ 发评论到一篇已删文章                            期望：400「文章不存在」
⑥ 删除文章后检查 Redis：
     EXISTS learning:article:detail:{id}  → 0
     EXISTS learning:article:views:{id}   → 0
     EXISTS learning:article:lock:{id}    → 0   ★ 补清后才为 0
```

**第 ④ 步是关键判据**：如果删文章后还能从缓存读到内容，说明 `cacheEvict` 漏了或者顺序错了。

### 6.4 全接口回归

逻辑删除影响**所有**查询，改完必须回归：用户 4 + 文章 5 + 分类 4 + 评论 3 = **16 个接口**全部重跑（含双账号的 403 分支）。

## 七、踩坑清单

| # | 坑 | 后果 | 避免方式 |
| --- | --- | --- | --- |
| 1 | `deleted` 建表用 `DEFAULT 1` | 所有历史数据变"已删除"，接口全 404 | `NOT NULL DEFAULT 0` |
| 2 | `deleted` 允许 `NULL` | `WHERE deleted=0` 对 NULL 不成立 → 该行永远查不到 | `NOT NULL` |
| 3 | 手写 `@Select` SQL 忘了带 `deleted=0` | 逻辑删除被绕过，已删数据照样查出 | 让逻辑删除字段不出现在业务 SQL 里，或每条手写 SQL 显式带上 |
| 4 | 在 `wrapper` 里再写 `.eq(Xxx::getDeleted, 0)` | 拼成 `deleted=0 AND deleted=0`，冗余 | 交给注解，业务代码不感知 |
| 5 | 以为 `deleteById` 还是物理删 | 数据一直在，表越来越大 | 知道它已被改写成 `UPDATE`；真要物理删得手写 SQL 或另写方法 |
| 6 | **忘了唯一索引还覆盖已删除行** | 同名永远无法复用（第三节） | 显式选方案并写进文档 |
| 7 | **删文章忘了清 `detail` 缓存** | 缓存里还能读到已删文章内容 | `deleteArticle` 里 `cacheEvict` 三个 key |
| 8 | **删文章忘了清 `views` key** | 无 TTL 的计数 key 永久堆积 | 同上 |
| 9 | 列表/详情接口测过就以为好了 | 逻辑删除影响**每个**查询，可能改坏未测的接口 | 走 6.4 全量回归 |
| 10 | 逻辑删除后才发现"回收站"没做 | 数据能恢复但没有恢复接口，只能改库 | 明确当前定位：**只做删除的软处理，不做恢复功能**（要恢复需另开接口，且要处理唯一索引冲突） |

## 八、面试怎么答

| 问题 | 答案要点 |
| --- | --- |
| **逻辑删除怎么实现？** | 表加 `deleted` 标记位 + MyBatis-Plus 的 `@TableLogic`。MP 在执行器层改写 SQL：查询自动拼 `deleted=0`，`deleteById` 变成 `UPDATE SET deleted=1`。**Service 层代码零改动** |
| **`@TableLogic` 有什么局限？** | 只管 MP 发起的操作 —— 手写 SQL（`@Select`/XML）完全绕过，必须自己带条件；另外它是"一删全隐"，不适合需要查已删数据的场景（回收站、审计） |
| ⭐ **逻辑删除和唯一索引会冲突吗？** | **会，而且必现**。唯一索引覆盖**物理行**，逻辑删除只改标记位 → 应用层查重看不见已删除行、数据库唯一索引看得见 → 用户"明明没人用这个名字却注册不了"。四种解法：删除时改名 / 索引带 `deleted`（只能删一次，不推荐）/ 索引带删除时间戳（生产标准）/ 明确接受不可复用 |
| **为什么索引带 `deleted` 不行？** | `UNIQUE(username, deleted)` 下，同名记录被删两次就有两条 `(name, 1)` → 第二条撞唯一键。**只能删除一次**，多删一次就失败 |
| **逻辑删除和缓存怎么配合？** | 删除时必须清缓存，否则命中缓存的请求会拿到已删除数据，**逻辑删除在缓存层被绕过**。这是逻辑删除最容易漏的一处 |
| **逻辑删除 vs 物理删除怎么选？** | 逻辑删除：可追溯、可恢复、不丢关联数据；代价是表膨胀、每个查询多一个条件、唯一索引受限。物理删除：干净，但删了就没了。**按合规/审计要求选，不要无脑上逻辑删除** |
| **表膨胀怎么办？** | 归档（定期把 `deleted=1` 搬到历史表）+ 分区。**不要用定时物理删 —— 那等于把逻辑删除的意义抵消掉** |
| **默认排除已删除数据是好事吗？** | 通常是，但做**统计/报表**时反而是坑：`COUNT(*)` 默认不含已删除，和历史数据对不上。要知道这个默认行为 |
