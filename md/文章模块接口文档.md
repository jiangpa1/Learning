# 文章模块接口文档

> 项目：Learning（Spring Boot 2.7.18 + MyBatis-Plus 3.5.5）
> Base URL：`http://localhost:8081`
> 前置：本模块所有接口都在 `/article/**` 下，**全部需要 token**（拦截器已覆盖 `/**`，只有 `/auth/**` 和 `/error` 放行）

---

## 一、通用说明

### 统一响应格式

沿用现有的 `Result` 结构：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": null
}
```

**提醒**：HTTP 状态码一律是 200，业务状态看响应体里的 `code`。

### 状态码

| code | 含义 | 本模块的触发场景 |
| --- | --- | --- |
| 200 | 成功 | 正常返回 |
| 400 | 参数或业务校验失败 | 标题为空、分类不存在 |
| 401 | 未登录 / token 无效 | 拦截器拦下 |
| **403** | **无权限** | **改／删别人的文章** |
| 404 | 资源不存在 | 文章 id 不存在 |
| 500 | 服务器内部错误 | 未预期异常 |

**403 需要新增。** 现在 `Result` 里有 200／400／401／404／500，缺 403。补一个：

```java
//6.无权限访问
public static <T> Result<T> forbidden(String message) {
    return new Result<>(403, message, null);
}
```

同时 `GlobalExceptionHandler` 用不着改——403 直接抛 `new BusinessException(403, "无权操作他人文章")`，现成的处理器会通过 `Result.build(e.getCode(), ...)` 把它带出去。

### 分页响应格式

列表接口返回的是分页对象，不是裸数组。直接返回 MyBatis-Plus 的 `IPage` 会带出 `orders`、`optimizeCountSql`、`searchCount` 等一堆前端用不上的字段，建议包一层：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "total": 42,
    "pageNum": 1,
    "pageSize": 10,
    "pages": 5,
    "records": [ ... ]
  }
}
```

对应新建一个 `PageResult<T>`（放 `com.jiangpa.common`），字段就这五个。

## 二、表结构

> **2026-09-19 核对**：本节四张表的建表语句已用 `SHOW CREATE TABLE` 与库里**实际结构**逐字对齐。
> 早期版本的表名是 `article` / `category` / `comment`（**无 `tb_` 前缀**），那是设计稿 —— 实际库和实体 `@TableName` 都是 **`tb_` 前缀**，已全部改正。

### tb_article（文章表）

```sql
CREATE TABLE `tb_article` (
  `id`          bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `user_id`     bigint       NOT NULL COMMENT '作者用户id',
  `title`       varchar(200) NOT NULL COMMENT '标题',
  `content`     text         NOT NULL COMMENT '正文',
  `summary`     varchar(255) DEFAULT NULL COMMENT '摘要，列表页展示用',
  `category_id` bigint       DEFAULT NULL COMMENT '分类id',
  `view_count`  int          NOT NULL DEFAULT '0' COMMENT '浏览量',
  `create_time` datetime     DEFAULT NULL COMMENT '创建时间',
  `update_time` datetime     DEFAULT NULL COMMENT '更新时间',
  `deleted`     tinyint      NOT NULL DEFAULT '0' COMMENT '逻辑删除 0=正常 1=已删',
  PRIMARY KEY (`id`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_create_time` (`create_time`),
  KEY `idx_category_id` (`category_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='文章表';
```

**索引为什么是这三个。** 列表默认按 `create_time` 倒序分页，走 `idx_create_time`；将来做"我的文章"要按 `user_id` 筛，走 `idx_user_id`；按分类筛选走 `idx_category_id`。索引不是越多越好——每个索引都会拖慢写入，所以只给**确定会用来做查询条件**的字段建。

`summary` 是这一版新加的，发布和修改文章时由后端从 `content` 截取生成，列表查询直接取这个字段，完全不用碰 `content`。

**表名为什么用 `user_id` 而不是 `author_id`。** 你的计划里表设计写的是 `user_id`，但下午那条又写"作为 author_id 写入"。作者本质上就是用户，两张表靠用户 id 关联，建议统一成 `user_id`——Java 实体里叫 `userId`，只有返回给前端的 VO 里才用 `authorNickname` 这种偏语义的名字来区分"这是作者的信息"。一个概念两个名字，后面写 join 的时候最容易搞混。

**四张表都有 `deleted` 列**（2026-09-18 加）。它是逻辑删除标记，实体上标 `@TableLogic`，MyBatis-Plus 在执行器层自动改写 SQL（查询自动拼 `deleted=0`，`deleteById` 变成 `UPDATE ... SET deleted=1`），**Service 层一行代码都没改**。详见 `逻辑删除设计文档.md`。

### tb_user（用户表）

实际表名是 **`tb_user`**，不是 `user`：

```sql
CREATE TABLE `tb_user` (
  `id`          bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键id',
  `username`    varchar(255) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci NOT NULL COMMENT '用户名',
  `nickname`    varchar(255) COLLATE utf8mb4_general_ci DEFAULT NULL,
  `role`        tinyint NOT NULL DEFAULT '0' COMMENT '0=user 1=admin',
  `avatar`      varchar(255) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '头像地址',
  `password`    varchar(255) COLLATE utf8mb4_general_ci DEFAULT NULL COMMENT '密码',
  `create_time` datetime DEFAULT NULL COMMENT '创建时间',
  `update_time` datetime DEFAULT NULL COMMENT '更新时间',
  `deleted`     tinyint NOT NULL DEFAULT '0',
  PRIMARY KEY (`id` DESC),
  UNIQUE KEY `uk_user_name` (`username`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;
```

三件事要知道：

- **`password` 存的是 BCrypt 密文**（60 字符），登录用 `matches` 比对，**绝不能存明文或 MD5**。表里若残留早期用 MD5 存的记录，`matches` 对 MD5 串只会返回 false → 现象是"密码明明是对的却登不上"，删掉重新注册即可。
- **`role` 由注册接口硬编码写 0**（fail-safe：忘了赋值的后果是"权限不足"，而不是"人人都是管理员"）。所以第一个管理员只能手工指定：
  ```sql
  UPDATE tb_user SET role = 1 WHERE username = '你的账号';
  ```
  **不做这步，`GET /user/list` 会返 403（包括你自己）。**
- **`avatar` 是设计稿留下的列**：库里确实建了，但 Java 实体 `User` 里**没有这个字段**，目前没有任何接口读写它 —— 属于"设计了但没实现"，不用管它。

### tb_category（分类表）

```sql
CREATE TABLE `tb_category` (
  `id`      bigint      NOT NULL AUTO_INCREMENT COMMENT '主键',
  `name`    varchar(50) NOT NULL COMMENT '分类名',
  `deleted` tinyint     NOT NULL DEFAULT '0' COMMENT '逻辑删除 0=正常 1=已删',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_name` (`name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分类表';
```

`name` 加唯一索引，防止出现两个"后端开发"分类。

> ⚠️ **但唯一索引覆盖物理行，所以删掉的名字无法复用** —— 逻辑删除后那一行的 `name` 还在，再建同名会撞 `uk_name`。这是**明确接受的取舍**（`逻辑删除设计文档.md` 第三节对比了四种方案，最终选方案 D），兜底文案是「数据不可复用！」。

### tb_comment（评论表）

```sql
CREATE TABLE `tb_comment` (
  `id`          bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `article_id`  bigint       NOT NULL COMMENT '文章id',
  `user_id`     bigint       NOT NULL COMMENT '评论人id',
  `content`     varchar(500) NOT NULL COMMENT '评论内容',
  `create_time` datetime     DEFAULT NULL COMMENT '创建时间',
  `deleted`     tinyint      NOT NULL DEFAULT '0' COMMENT '逻辑删除 0=正常 1=已删',
  PRIMARY KEY (`id`),
  KEY `idx_article_create` (`article_id`,`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='评论表';
```

**索引为什么是复合的，而不是单列 `idx_article_id`。** 评论列表的查询是 `WHERE article_id = ? ORDER BY create_time DESC`。单列索引只能过滤，过滤完 MySQL 还要再排一次序；复合索引**等值列在前、排序列在后**，让过滤和排序一次扫描完成。实测对比（同一张表用 `IGNORE INDEX` 对照）：

| 索引 | `EXPLAIN` 的 `Extra` |
| --- | --- |
| `idx_article_id`（单列，早期设计） | **`Using filesort`** —— 多一次排序 |
| `idx_article_create (article_id, create_time)`（现用） | **`Backward index scan`** —— 无 filesort |

**加完复合索引要把被它最左前缀完全覆盖的单列索引删掉** —— 索引不是越多越好，每个索引都要在写入时同步维护：

```sql
ALTER TABLE tb_comment ADD INDEX idx_article_create (article_id, create_time);
DROP INDEX idx_article_id ON tb_comment;
```

**关于外键：上面四张表都没有建 `FOREIGN KEY`，这是故意的。** 互联网项目普遍不用物理外键——外键会在每次写入时加锁检查、影响并发性能，而且分库分表之后根本无法维护。关联关系的正确性由**应用层 + 索引**保证。这也是《阿里巴巴 Java 开发手册》里明确要求的。

> **如果你手上是一个更早的库**：需要补的增量 DDL（四张表加 `deleted`、`tb_user` 加 `role`、评论表换复合索引）见 `LearningHANDOFF.md` 第三节第 3 条，那里是当时实际执行过的 `ALTER` 记录。
>
> 分类和评论两张表当年是"先建好备用"，现在**四个模块都已实现**（分类 4 接口 + 评论 3 接口，见 `分类与评论模块接口文档.md`）。

## 四、接口详情

### 1. 文章详情

```
GET /article/{id}
Authorization: Bearer {{token}}
```

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 文章主键 |

**成功响应**

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "id": 1,
    "title": "MySQL 索引为什么用 B+ 树",
    "content": "完整的正文……",
    "userId": 1,
    "authorNickname": "张三",
    "categoryId": 2,
    "viewCount": 43,
    "createTime": "2026-09-13T10:30:00",
    "updateTime": "2026-09-13T10:30:00"
  }
}
```

**失败响应**

```json
{ "code": 404, "message": "文章不存在", "data": null }
```

**服务端要做的事**

- 按 id 查文章，不存在抛 `BusinessException(404, "文章不存在")`
- 查作者昵称，一起返回
- **把 `view_count` 加一**（见第五节第 4 点的并发处理）
- 返回完整正文，所以这里叫 `ArticleDetailVO`

### 2. 文章列表（分页）

```
GET /article/list?pageNum=1&pageSize=10
Authorization: Bearer {{token}}
```

**查询参数**

| 参数 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| pageNum | Integer | 否 | 1 | 页码，从 1 开始 |
| pageSize | Integer | 否 | 10 | 每页条数，**上限 50** |

**成功响应**

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "total": 42,
    "pageNum": 1,
    "pageSize": 10,
    "pages": 5,
    "records": [
      {
        "id": 1,
        "title": "MySQL 索引为什么用 B+ 树",
        "summary": "MySQL 索引底层用的是 B+ 树，而不是 B 树或哈希表…",
        "userId": 1,
        "authorNickname": "张三",
        "viewCount": 43,
        "createTime": "2026-09-13T10:30:00"
      }
    ]
  }
}
```

**列表和详情返回的字段不一样，这是有意的。**

列表里**没有 `content`**，只有 `summary`；也没有 `updateTime`。这叫"列表页轻量、详情页完整"。判断依据很简单：列表页一屏要展示十条，如果每条都拖着几 KB 的正文，一次请求就是几十 KB，而且用户根本没展开看。字段越少，数据库要读的数据越少、网络传输越小、前端渲染越快。

`pageSize` 要设上限。不设的话前端传个 `pageSize=100000`，你的数据库就得一次吐出全表——这是个很容易被忽略的性能漏洞，也是面试常问的点。

### 3. 发布文章

```
POST /article
Authorization: Bearer {{token}}
Content-Type: application/json
```

**请求体**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| title | String | 是 | 标题，长度 1–200 |
| content | String | 是 | 正文，不能为空 |
| categoryId | Long | 否 | 分类 id |

```json
{
  "title": "MySQL 索引为什么用 B+ 树",
  "content": "完整的正文……",
  "categoryId": 2
}
```

**成功响应**

```json
{ "code": 200, "message": "操作成功", "data": 1 }
```

`data` 直接返回新文章的 id。

**服务端要做的事**

- **作者 id 从 JWT 里取，绝对不能从前端传。** Controller 方法参数写 `@RequestAttribute("userId") Long userId`，拦截器已经把这个值塞进 request 了。如果做成从请求体读 `userId`，那任何人都能指定别人的 id 去发文——这是很典型的越权漏洞。
- 从 `content` 生成 `summary` 存进去
- `viewCount` 初始为 0，`createTime`、`updateTime` 由服务端生成

**摘要怎么生成**

规则建议：去掉换行和首尾空格 → 截取前 100 个字符 → 原文更长的话末尾加 `……`。写成一个私有方法放在 Service 里就行。

有个细节要留意：如果你的正文将来支持富文本（带 `<p>` `<strong>` 这类标签），截取前必须先把标签去掉，否则摘要里会出现半截 HTML。现在存纯文本的话不用管，但知道有这回事。

### 4. 修改文章

```
PUT /article/{id}
Authorization: Bearer {{token}}
Content-Type: application/json
```

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 要修改的文章 id |

**请求体**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| title | String | 是 | 标题 |
| content | String | 是 | 正文 |
| categoryId | Long | 否 | 分类 id |

```json
{
  "title": "MySQL 索引为什么用 B+ 树（修订）",
  "content": "修改后的正文……",
  "categoryId": 2
}
```

注意请求体里**没有 `id`**——id 已经在路径上了，再从 body 传一遍就有了两个来源，读代码的人会不知道以哪个为准。

**成功响应**

```json
{ "code": 200, "message": "操作成功", "data": null }
```

**失败响应**

```json
{ "code": 403, "message": "无权操作他人文章", "data": null }
```

**服务端要做的事**

- 先按 id 查文章，不存在抛 404
- **校验作者身份**：`article.getUserId()` 和当前登录的 `userId` 不相等，抛 `BusinessException(403, "无权操作他人文章")`
- 重新生成 `summary`
- 更新 `title`、`content`、`summary`、`categoryId`、`updateTime`
- **`createTime` 不能被覆盖，`viewCount` 不能被重置**——这两条是下午计划里特意点出来的，具体怎么保证见第五节第 4 点

### 5. 删除文章

```
DELETE /article/{id}
Authorization: Bearer {{token}}
```

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 文章主键 |

**成功响应**

```json
{ "code": 200, "message": "操作成功", "data": null }
```

**失败响应**：404（文章不存在）或 403（不是作者）

**服务端要做的事**

- 查文章，不存在抛 404
- 校验作者身份，不是本人抛 403——**顺序不能反**：先判存在再判权限，否则文章不存在时会返回 403，让人以为是没有权限

> 真实项目里删除一般做**逻辑删除**（加个 `deleted` 字段标记），而不是真的 `DELETE`。这样误删能恢复，历史数据也留得住。这个后面可以再优化，现在物理删除也行。

## 五、关键实现点

这几处是这轮最容易卡住的地方，动手前先看一眼。

### 1. 分页插件必须先配置，否则分页不生效

这是最经典的坑：**不配分页插件，`selectPage` 不报错，但 LIMIT 不会拼进 SQL，它会把整张表查出来再在内存里截取。** 数据少的时候完全看不出问题，等表里几万条时才会发现接口突然变慢。

新建 `com.jiangpa.config.MybatisPlusConfig`：

```java
@Configuration
public class MybatisPlusConfig {

    @Bean
    public MybatisPlusInterceptor mybatisPlusInterceptor() {
        MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
        interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
        return interceptor;
    }
}
```

注意用 `MybatisPlusInterceptor`（3.5.x 的写法），不要用 `PaginationInterceptor`——那是老版本已经被废弃的类，搜出来的老教程里很多。

### 2. 分页的基本写法

```java
Page<Article> page = new Page<>(pageNum, pageSize);

LambdaQueryWrapper<Article> wrapper = new LambdaQueryWrapper<>();
wrapper.select(Article::getId, Article::getTitle, Article::getSummary,
               Article::getUserId, Article::getViewCount, Article::getCreateTime)
       .orderByDesc(Article::getCreateTime);

IPage<Article> result = articleMapper.selectPage(page, wrapper);
```

关键在 `select(...)` 那句：**只查列表需要的列，不查 `content`**。这就是"列表轻量"在代码层面的落地方式。不写这行的话，MP 默认 `SELECT *`，正文照样被拉出来，前面的设计就白做了。

### 3. 作者昵称怎么查——别写成 N+1

列表和详情都要显示作者昵称，而 `tb_article` 表里只有 `user_id`。有两种做法。

**做法一（推荐先用这个）：分步查询。**

拿到本页文章后，把所有 `userId` 收集成一个集合，**用一次查询**批量取出这些用户：

```java
List<Long> userIds = articles.stream().map(Article::getUserId).distinct().toList();
List<User> users = userMapper.selectBatchIds(userIds);
Map<Long, String> nicknameMap = users.stream()
        .collect(Collectors.toMap(User::getId, User::getNickname));
```

然后遍历文章，从 map 里取昵称填进 VO。整个列表接口总共只查两次数据库，跟页大小无关。

**做法二：写 XML 自定义 SQL，用 join 一次查出来。** 性能更好，但要新增 `resources/mapper/ArticleMapper.xml`。等这个模块跑通、你熟悉了 MP 之后再回去优化，是个很好的练习。

**为什么不能边遍历边查。** 如果你写成：

```java
for (Article a : articles) {
    User u = userMapper.selectById(a.getUserId());   // 千万不要
    ...
}
```

一页 10 条就是 11 次数据库查询，一页 50 条就是 51 次。这就是 **N+1 查询问题**，是面试里的高频考点，也是线上接口变慢最常见的原因之一。记住一句话：**不要在循环里查数据库。**

### 4. 更新时怎么保护 createTime 和 viewCount

MP 的 `updateById` 默认只更新非 null 字段——听起来正好，但这里有个陷阱。

你的 `viewCount` 是 `int`（基本类型）。如果新建一个 `Article` 对象、只 set 要改的字段，那么 `viewCount` 因为没赋值就是 `0`，**不是 null**，`updateById` 会把你辛苦攒的浏览量重置成 0。

所以推荐不要用 `updateById`，改用 `LambdaUpdateWrapper` **显式指定要更新哪几列**：

```java
LambdaUpdateWrapper<Article> wrapper = new LambdaUpdateWrapper<>();
wrapper.eq(Article::getId, id)
       .set(Article::getTitle, dto.getTitle())
       .set(Article::getContent, dto.getContent())
       .set(Article::getSummary, summary)
       .set(Article::getCategoryId, dto.getCategoryId())
       .set(Article::getUpdateTime, LocalDateTime.now());

articleMapper.update(null, wrapper);
```

只 set 了该改的列，`create_time` 和 `view_count` 根本没出现在 SQL 里，自然不会被动。这是最稳的写法。

（另一种思路是把实体所有字段都用包装类 `Integer`，靠 null 策略跳过。但那样每加一个字段都得记得用包装类，不如显式指定列来得可靠。）

### 5. 浏览量为什么不能用"查出来加一再写回"

在详情接口里累加浏览量，**必须用 SQL 层的自增**：

```java
LambdaUpdateWrapper<Article> wrapper = new LambdaUpdateWrapper<>();
wrapper.eq(Article::getId, id).setSql("view_count = view_count + 1");
articleMapper.update(null, wrapper);
```

不要写成：

```java
article.setViewCount(article.getViewCount() + 1);   // 并发下会丢更新
articleMapper.updateById(article);
```

因为后者是"读—改—写"三步。两个请求同时读到时都是 43，各自加一都写回 44，实际应该 45——一次浏览凭空消失了。交给数据库做 `view_count = view_count + 1`，这一句本身是原子的，不存在这个问题。

这就是典型的**更新丢失**问题，也是面试常问的并发场景。

### 6. 时间字段可以改成自动填充

你现在 `UserServiceImpl` 里有四处手写 `LocalDateTime.now()`。文章模块再加几处，到处都是这个调用，容易漏写。

MyBatis-Plus 支持自动填充：给字段加 `@TableField(fill = FieldFill.INSERT)`（新增时填）和 `@TableField(fill = FieldFill.INSERT_UPDATE)`（新增和修改都填），再实现一个 `MetaObjectHandler` 就行。

这不是必须的，手工写也能跑。但字段一多，自动填充能省掉一大类"忘了设 updateTime"的低级 bug。可以这轮先手工写，等文章模块跑通了再统一改。

### 7. VO 要分层

这轮涉及三种返回形态，别用同一个类硬凑：

| 类名 | 用途 | 包含字段 |
| --- | --- | --- |
| `ArticleListVO` | 列表项 | id、title、summary、userId、authorNickname、viewCount、createTime |
| `ArticleDetailVO` | 详情 | 上面全部 + content、categoryId、updateTime |
| `ArticleDTO` | 接收发布／修改的入参 | title、content、categoryId |

注意 `ArticleDTO` 里**没有 `userId`**——作者只能从 JWT 取。这与前面第 3 点呼应。

## 七、两点提醒

**一是路径风格跟用户模块不一致。** 用户模块的修改接口是 `PUT /user`、id 放在请求体里；文章模块你设计的是 `PUT /article/{id}`、id 放在路径里。REST 风格下后者更规范（id 是资源标识，就该在路径上）。两种都行，但**同一个项目里最好统一**。建议文章模块按路径参数来写，回头找时间把用户模块那两个接口也改过来，顺便更新那份接口文档。

**二是这轮涉及的问题比用户模块多。** 分页、跨表查询、权限校验、并发更新，每一个都是能展开讲的知识点。上午的两个查询接口先把分页和跨表这两件事做透，下午的三个写接口再集中处理权限和字段保护，别一次全铺开。
