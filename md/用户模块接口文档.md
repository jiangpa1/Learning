> 项目：Learning（Spring Boot 2.7.18 + MyBatis-Plus 3.5.5 + JWT 双 Token + Redis）
> 对应实体：`com.jiangpa.pojo.User`／数据表：`tb_user`
> Base URL：`http://localhost:8080`
> 文档状态：**已按实际实现重写**（2026-09-19）。早期设计稿见第八节「设计演进对照」。

## 一、通用说明

**数据格式**：请求与响应统一使用 `application/json`，编码 UTF-8。

### 统一响应格式

所有接口都返回同一个 `Result` 结构，前端只需处理一套逻辑。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | Integer | 业务状态码，200 表示成功 |
| message | String | 提示信息，失败时给出原因 |
| data | Object | 业务数据，失败时为 `null` |

```json
{
  "code": 200,
  "message": "操作成功",
  "data": null
}
```

> ⚠️ **HTTP 状态码恒为 200**，业务状态放在响应体的 `code` 里。前端判断成功失败**必须看 body 的 `code`**，不能看 HTTP 状态码。这是全项目铁律（鉴权失败、参数错误、限流、服务器异常在 HTTP 层都是 200）。

### 状态码约定

| code | 含义 | 使用场景 | 前端该做什么 |
| --- | --- | --- | --- |
| 200 | 成功 | 正常返回 | — |
| 400 | 参数错误 | 必填字段为空、格式不合法、**请求体解析失败**、唯一键冲突 | 提示用户改输入 |
| 401 | 未认证 / 凭证失效 | 未带 token、token 过期/篡改、已登出、token 类型错 | 用 refreshToken 换新；换不到**跳登录页** |
| 403 | 无权限 | **归属校验失败**（动别人的资源）、**角色不足**（非管理员调管理接口） | 提示"无权操作"，**不要跳登录页** |
| 404 | 资源不存在 | 按 id 查询/修改/删除时找不到记录（含**已逻辑删除**的） | 提示资源不存在 |
| 429 | 请求过于频繁 | 触发接口限流 | 提示"操作太频繁"，按 `Retry-After` 等待，**不要跳登录页** |
| 500 | 服务器内部错误 | 未预期的异常 | 提示稍后重试、上报 |
| 503 | 服务暂时不可用 | **认证服务不可用**（Redis 挂了，黑名单/凭证查不了） | 提示稍后重试，**保留 token** |

> **401 / 403 / 429 / 503 四者的区分很重要**：401 是"你的凭证有问题"（跳登录页），403 是"你没权限"（不跳），429 是"你太快了"（等着重试），503 是"服务端暂时坏了"（保留凭证）。**互相混用会让前端做错动作。**

### 关于密码

**任何接口的响应都不包含 `password` 字段。** 返回给前端的是 `UserVO`，不是 `User` 实体。

### UserVO 结构

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | Long | 用户主键 |
| role | Integer | **角色：0=普通用户，1=管理员** |
| username | String | 用户名 |
| nickname | String | 昵称 |

```json
{ "id": 18, "role": 0, "username": "zhangsan", "nickname": "zhangsan" }
```

> ⚠️ **`role` 会返回给前端**。它不是敏感信息（就是 0/1），前端可以据此决定是否显示管理入口；但**它不代表前端可以信任自己的权限判断** —— 所有权限校验都在服务端做。

### 鉴权方式

除 `/auth/**` 外，所有接口都需要在请求头带 access token：

```
Authorization: Bearer <accessToken>
```

### 角色与权限（本模块的核心规则）

本模块同时存在**两类**授权，机制不同、**不能互相替代**：

| 越权类型 | 例子 | 判定依据 | 机制 |
| --- | --- | --- | --- |
| **水平越权** | A 改/删 B 的账号 | 资源**有主** | **归属校验** → 403 |
| **纵向越权** | 普通用户拉全站用户列表、改角色 | 资源**无主（全站资产）** | **角色校验**（`@RequireRole`）→ 403 |

**首任管理员必须手工指定**（注册接口硬编码 `role = 0`，这是 fail-safe 设计）：

```sql
UPDATE tb_user SET role = 1 WHERE username = '你的账号';
```

### 逻辑删除

用户删除是**逻辑删除**（`@TableLogic` + `deleted` 字段），不是物理删除：

- 接口层看不到已删除用户（查询自动带 `deleted = 0`），返回 404；
- **物理行仍在表里**（`deleted = 1`），可追溯；
- **已删除的用户名不可复用** —— 唯一索引 `uk_user_name` 覆盖物理行，再注册同名会返回 400「数据不可复用！」。这是明确的取舍（详见 `md/逻辑删除设计文档.md`）。

### 接口限流

| 接口 | 阈值 |
| --- | --- |
| `POST /auth/register` | 5 次/分钟（按 IP） |
| `POST /auth/login` | 10 次/分钟（按 IP） |
| `GET /user/list` | 30 次/分钟（按用户） |

超限返回 `code=429`，并带响应头 `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset` / `Retry-After`（秒）。

## 二、接口总览

**认证接口**（`/auth/**`，无需 token）：

| 序号 | 功能 | 方法 | 路径 |
| --- | --- | --- | --- |
| 1 | 注册 | POST | `/auth/register` |
| 2 | 登录（返回双 Token） | POST | `/auth/login` |
| 3 | 续期（refresh 轮转） | POST | `/auth/refresh` |
| 4 | 登出 | POST | `/auth/logout` |

**用户接口**（`/user/**`，需 token）：

| 序号 | 功能 | 方法 | 路径 | 权限 |
| --- | --- | --- | --- | --- |
| 5 | 查询单个用户 | GET | `/user/{id}` | 自己 **或** 管理员 |
| 6 | 查询用户列表（分页） | GET | `/user/list` | **仅管理员** |
| 7 | 修改用户（昵称） | PUT | `/user/{id}` | **仅本人** |
| 8 | 删除用户（逻辑删除） | DELETE | `/user/{id}` | 自己 **或** 管理员 |
| 9 | 修改角色 | PUT | `/user/role` | **仅管理员** |

> **注意 id 的位置不统一**：`PUT /user/{id}` 的 id 在**路径**，而 `PUT /user/role` 的 id 在**请求体**（`{id, role}` 两个字段一起校验）。文档里以实际为准。

## 三、认证接口

### 1. 注册

**请求**

```
POST /auth/register
Content-Type: application/json
```

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| username | String | 是 | 用户名，唯一，长度 4–20 |
| password | String | 是 | 密码，长度 6–20，服务端 BCrypt 加密后存储 |
| nickname | String | 否 | 昵称，不传或空白则默认为用户名 |

**请求示例**

```json
{ "username": "zhangsan", "password": "123456", "nickname": "张三" }
```

**成功响应**

```json
{
  "code": 200,
  "message": "操作成功",
  "data": { "id": 18, "role": 0, "username": "zhangsan", "nickname": "张三" }
}
```

**失败响应**

| 场景 | code | message |
| --- | --- | --- |
| 用户名已存在（应用层查重） | 400 | 用户名已存在！ |
| **用户名曾被使用并已删除**（唯一索引兜底） | 400 | 数据不可复用！ |
| 用户名长度不在 4–20 | 400 | 用户名长度必须在 4-20 位之间 |
| 密码长度不在 6–20 | 400 | 密码长度必须在 6-20 位之间 |
| 触发限流（5 次/分钟） | 429 | 操作太频繁，请等待 N 秒 |

**服务端做的事**

- 校验 `username` 是否已存在 → 400（**常态路径，给友好提示**）
- 数据库唯一索引 `uk_user_name` 作为**并发兜底** → `DuplicateKeyException` → 400（**两条路径缺一不可**：只有查重则并发下会插入重复；只有索引则用户看到 500）
- 密码 BCrypt 加密后存，**不存明文**
- **`role` 硬编码为 0**，绝不接受客户端传入（否则任何人可注册成管理员）；响应里显式 set 0，保证与库里的 `DEFAULT 0` 一致
- `createTime` / `updateTime` 服务端生成

### 2. 登录

**请求**

```
POST /auth/login
Content-Type: application/json
```

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| username | String | 是 | 用户名 |
| password | String | 是 | 密码 |

**成功响应**（返回**双 Token**）

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
    "refreshToken": "eyJhbGciOiJIUzI1NiJ9...",
    "expiresIn": 1800000
  }
}
```

| 字段 | 说明 |
| --- | --- |
| accessToken | 短期凭证（**30 分钟**），调业务接口时放在 `Authorization: Bearer` |
| refreshToken | 长期凭证（**7 天**），**只用来调 `/auth/refresh`** |
| expiresIn | access token 有效**毫秒数**。前端据此**提前 60 秒主动刷新**，用户无感 |

**失败响应**：`code=400`，message 统一为 **「用户名或密码错误」** —— 用户不存在和密码错误返回**完全相同**的提示，防止用户名枚举。

> **access token 的 payload**（base64 明文，**别放敏感信息**）：
> ```json
> { "role":1, "id":17, "type":"access", "username":"lisi", "sub":"17",
>   "jti":"<uuid>", "iss":"learning", "iat":..., "exp":... }
> ```
> `type` claim 必须校验（两个 token 同密钥、同结构，只靠 `type` 区分）。

**服务端做的事**：`UserService.authenticate` 只负责认证 → `TokenService.issue` 负责签发（**分离是为了避免循环依赖**）。签发时把 refreshToken 的 **SHA-256 哈希**写入 `learning:token:refresh:{userId}`（TTL 7 天）—— 用 userId 做 key 意味着**新登录会顶掉旧凭证，天然单端登录**。

---

### 3. 续期（refresh 轮转）

**请求**

```
POST /auth/refresh
Content-Type: application/json
```

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| refreshToken | String | 是 | 登录时拿到的 refreshToken |

**请求示例**

```json
{ "refreshToken": "eyJhbGciOiJIUzI1NiJ9..." }
```

**成功响应**：与登录相同结构，返回**全新的一对 Token**。

**关键语义：轮转（rotation）** —— 旧 refreshToken **当场作废**，即使用它自身还没过期。前端**必须把新的 refreshToken 存下来**，漏了就掉线。

**失败响应**

| 场景 | code | message |
| --- | --- | --- |
| token 已过期 | 401 | 登录已过期，请重新登陆 |
| 签名被篡改 / 结构损坏 | 401 | token 无效 |
| 传的是 accessToken（类型不对） | 401 | token类型错误 |
| 已被轮转/被登出/被顶号 | 401 | 登录已失效，请重新登陆 |
| 认证服务不可用（Redis 挂了） | 503 | 服务暂时不可用 |
| refreshToken 为空 | 400 | （字段校验提示） |

> ⚠️ **并发刷新必须前端去重**：页面上 5 个请求同时 401 → 若各自去刷新，轮转下只有第一个成功、其余全失败 → 用户莫名掉线。做法：第一个 401 触发刷新，其余请求挂起等结果，复用同一对新 token。

---

### 4. 登出

**请求**

```
POST /auth/logout
Authorization: Bearer <accessToken>
```

无请求体。

**成功响应**

```json
{ "code": 200, "message": "操作成功", "data": null }
```

**服务端做的事**

- 删掉 `learning:token:refresh:{userId}` → **立即无法续期**
- 把当前 accessToken 的哈希写入**黑名单** `learning:token:blacklist:{sha256}`，**TTL = 该 token 的剩余有效期**（不是固定值）→ access 立即失效

**边界行为（已实测）**

| 情况 | 行为 |
| --- | --- |
| 带**已过期**的 accessToken 登出 | **仍返回 200** 且 refreshKey 被删（用户的意图是登出，不是证明 token 有效） |
| 不带 token / token 格式非法 | 返回 200（幂等，前端清本地状态即可） |
| **Redis 不可用** | **503**（写黑名单失败 = access 没被作废，不能声称登出成功） |

> 黑名单写失败为什么必须 fail-closed 而删 refreshKey 失败可以 fail-open：删失败只是少了一层保险（access 已进黑名单）；**写失败等于 access 完全没被作废**，返回 200 会让用户以为退了，实际那个 token 在剩余 30 分钟内仍然有效。

## 四、用户接口

### 5. 查询单个用户

```
GET /user/{id}
Authorization: Bearer <accessToken>
```

**路径参数**：`id` (Long, 必填)

**权限**：**自己 或 管理员**（普通用户查别人 → 403）

**成功响应**

```json
{
  "code": 200, "message": "操作成功",
  "data": { "id": 18, "role": 0, "username": "zhangsan", "nickname": "zhangsan" }
}
```

**失败响应**

| 场景 | code | message |
| --- | --- | --- |
| id 不存在（或已逻辑删除） | 404 | 用户不存在！ |
| 普通用户查别人的资料 | 403 | 无权操作他人账号 |

> **404 优先于 403**：先判存在（404）再判归属（403）。顺序反了会让"查一个不存在的用户"返回 403，误导排查方向，而且 `user` 为 null 时 `getUserId()` 会 NPE。

---

### 6. 查询用户列表（分页）

```
GET /user/list?pageNum=1&pageSize=10
Authorization: Bearer <accessToken>
```

**请求参数（Query）**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| pageNum | Integer | 否 | 1 | 页码，从 1 开始 |
| pageSize | Integer | 否 | 10 | 每页条数，**上限 50**（超出自动截断，不报错） |

**权限**：**仅管理员**（普通用户 → 403）。这是**纵向越权**防护 —— 全站用户列表属于"无主资产"，只能用角色校验。

**成功响应**

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "total": 4,
    "pageNum": 1,
    "pageSize": 10,
    "pages": 1,
    "records": [
      { "id": 19, "role": 0, "username": "authtest61867", "nickname": "authcheck" },
      { "id": 18, "role": 0, "username": "zhangsan", "nickname": "zhangsan" },
      { "id": 17, "role": 1, "username": "lisi", "nickname": "lisi" }
    ]
  }
}
```

| 字段 | 说明 |
| --- | --- |
| total | 总记录数（**不是当前页条数**） |
| pages | 总页数 |
| records | 当前页数据数组 |

**空结果**：`records` 返回 `[]`，`total` 为 0，**不返回 null**。

**实现要点**：`wrapper.select(...)` **只查需要的列**（id/role/username/nickname），不 `SELECT *` —— 用户表将来加了大字段（头像 URL、个人简介）时，列表接口不会把它们全拉出来。查询**自动带 `deleted = 0`**（`@TableLogic`）。

### 7. 修改用户（昵称）

```
PUT /user/{id}
Authorization: Bearer <accessToken>
Content-Type: application/json
```

**路径参数**：`id` (Long, 必填)

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | **是** | 用户主键（`@NotNull` 校验，**必须与路径 id 一致**） |
| nickname | String | 否 | 新昵称 |

**请求示例**

```json
{ "id": 18, "nickname": "张三丰" }
```

**权限**：**仅本人**（管理员也**不能**改别人的昵称 —— 昵称属个人信息）

**失败响应**

| 场景 | code | message |
| --- | --- | --- |
| id 不存在 | 404 | 用户不存在！ |
| 改别人的昵称 | 403 | 无权操作他人账号 |
| Body 里没传 id | 400 | 用户id不能为空 |

**服务端做的事**：先判存在（404）→ 再判归属（403）→ 只更新 `nickname` 和 `updateTime`。

**关于密码**：`username` 是登录标识**不允许修改**；改密码应另开独立接口，且**改完必须显式删该用户的 refreshKey 强制下线**（参考 `PUT /user/role` 的做法）。

---

### 8. 删除用户（逻辑删除）

```
DELETE /user/{id}
Authorization: Bearer <accessToken>
```

**权限**：**自己 或 管理员**

**成功响应**

```json
{ "code": 200, "message": "操作成功", "data": null }
```

**失败响应**

| 场景 | code | message |
| --- | --- | --- |
| id 不存在（或已删除） | 404 | 用户不存在！ |
| 删别人的账号 | 403 | 无权操作他人账号 |

**服务端做的事**

- 先 `selectById` 判存在 → 404（**重复删除同一个 id 会返回 404 而不是 200**，因为已删除的记录查不到）
- 再判归属 → 403
- `deleteById` **不是物理删除**：`@TableLogic` 把它改写成 `UPDATE tb_user SET deleted = 1 WHERE id = ? AND deleted = 0`
- **数据库不建物理外键**，所以用户删除后他的文章、评论仍然存在（靠应用层保证，见 `md/逻辑删除设计文档.md`）

### 9. 修改角色

```
PUT /user/role
Authorization: Bearer <accessToken>
Content-Type: application/json
```

> ⚠️ **id 在请求体里**，不在路径里。

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 目标用户主键 |
| role | Integer | 是 | **0 = 降级为普通用户，1 = 升级为管理员**（只接受 0/1） |

**请求示例**

```json
{ "id": 18, "role": 1 }
```

**权限**：**仅管理员**（`@RequireRole(1)`）。**普通用户永不可改** —— 这是最重要的一条：如果这里能被普通用户调用，就等于**提权漏洞**（比删数据严重得多）。

**成功响应**

```json
{ "code": 200, "message": "操作成功", "data": null }
```

**失败响应**

| 场景 | code | message |
| --- | --- | --- |
| 普通用户调用 | 403 | 无权限！ |
| id 不存在 | 404 | 用户不存在！ |
| role 不在 0/1 之间 | 400 | 权限值只能是 0(降级) 或 1(升级) |
| 没传 role | 400 | 权限设定不能为空！ |
| 没传 id | 400 | 用户id不能为空 |
| **降级最后一个管理员** | 403 | 无法降级最后一位管理员 |

**服务端做的事**

1. 判存在 → 404
2. **守卫**：若目标当前是管理员、且本次要降为 0，则检查"除他之外还有没有管理员"，没有 → 403（否则系统会**永久失去管理能力**，只能改库恢复）
3. 落库
4. **无条件删除该用户的 refreshKey** → 让他的旧凭证**无法续期**

> **为什么第 4 步很重要，且要放在守卫之后、落库之后**：role 写在 JWT claim 里，而 `refresh` 是**从旧 token 的 claims 取 role** 再签发新 token。所以只要旧 refreshToken 还能用，**旧角色就能被无限续期** —— 不清理的话"降级"等于没降。实测过：修复前降级普通用户后，用降级前的 refreshToken 仍能换出新 token 并继承旧 role。
>
> **已知残留**：accessToken 无状态，改角色后**它最多还能用 30 分钟**（无法立即吊销）。删 refreshKey 保证的是"无法续期"，不是"立即失效"。要立即失效需引入"角色版本号"比对。

## 五、完整调用流程示例

```bash
# ① 注册
POST /auth/register   {"username":"zhangsan","password":"123456"}

# ② 登录拿双 Token
POST /auth/login      {"username":"zhangsan","password":"123456"}
#   → { accessToken, refreshToken, expiresIn }

# ③ 带 accessToken 访问业务接口
GET  /user/18         Authorization: Bearer <accessToken>

# ④ 临近过期时主动续期（前端提前 60 秒）
POST /auth/refresh    {"refreshToken":"<refreshToken>"}
#   → 新的一对 Token，旧 refreshToken 当场作废

# ⑤ 登出
POST /auth/logout     Authorization: Bearer <accessToken>
#   → refreshKey 被删 + accessToken 进黑名单
```

## 六、容易踩的测试要点

写测试用例时这几类边界**只有刻意构造才会碰到**（都真实踩过）：

- **权限分支必须用第二个账号** —— 用同一个账号永远改自己的东西、永远成功，403 那条分支触发不到
- **权限用例要成对测** —— 既测"该拒绝的拒绝了"，也测"**该放行的放行了**"。`!A || !B` 写成 `!A && !B` 时，"查别人 → 403"这条**恰好还是对的**，只测它发现不了 bug
- **`@Valid` 是否真的生效** —— 发一个明确越界的值（如 `role=9`），看是否被拒。**漏写 `@Valid` 会让整组约束静默失效**，接口不报错、返回 200 但脏数据已落库
- **404 与 403 的先后** —— 查/删一个**不存在**的 id，期望 404 而不是 403
- **重复删除** —— 期望 404（不是 200）
- **已删除的用户名能否复用** —— 期望 400「数据不可复用！」
- **请求体格式错误** —— 发截断的 JSON，期望 **400**（不是 500）
- **限流** —— 连打超过阈值，期望 **429** + `Retry-After` 头

## 七、常见的"看起来对但其实是坑"的写法

| 写法 | 问题 |
| --- | --- |
| `claims.get("role", String.class)` | jjwt 类型 getter 是**精确比对**。payload 里 role 是 JSON 数字，取 String 会抛 `RequiredTypeException`（继承 `JwtException`）→ 被拦截器兜底 catch 吞掉 → **所有带合法 token 的请求返 401**。用 `Number.class` |
| `!Objects.equals(id, userId) \|\| !Objects.equals(role, 1)` | 等价于"必须同时是自己**且**是管理员"。要表达"自己 **或** 管理员"，拒绝条件应是 `!A && !B` |
| `updateRole(@RequestBody DTO)`（漏 `@Valid`） | 约束注解只是元数据，**没有 `@Valid` 就不触发校验** → 越界值直接落库 |
| `wrapper.select(...)` 后的 `User` 当完整实体用 | 这是**部分字段实体**（password/deleted/createTime 均为 null）。只能用于映射 VO，拿去做认证会 NPE 或判定失败 |
| 把 `role` 放进注册/更新 DTO | **任何人可注册成管理员或自我提权**。role 永不进请求 DTO；注册硬编码 0；改角色走独立接口 + `@RequireRole(1)` |
