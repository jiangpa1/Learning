# 用户模块接口文档

> 项目：Learning（Spring Boot 2.7.18 + MyBatis-Plus 3.4.3）
> 对应实体：`com.jiangpa.pojo.User`／数据表：`tb_user`
> Base URL：`http://localhost:8080`

---

## 一、通用说明

**数据格式**：请求与响应统一使用 `application/json`，编码 UTF-8。

### 统一响应格式

所有接口都返回同一个 `Result` 结构，前端只需处理一套逻辑。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| code | Integer | 业务状态码，200 表示成功 |
| message | String | 提示信息，失败时给出原因 |
| data | Object | 业务数据，失败时为 `null` |

```json
{
  "code": 200,
  "message": "success",
  "data": null
}
```

### 状态码约定

| code | 含义 | 使用场景 |
| --- | --- | --- |
| 200 | 成功 | 正常返回 |
| 400 | 参数错误 | 必填字段为空、格式不合法 |
| 404 | 资源不存在 | 按 id 查询／修改／删除时找不到记录 |
| 500 | 服务器内部错误 | 未预期的异常 |

### 时间格式

`createTime`、`updateTime` 为 `LocalDateTime`，JSON 中序列化为 ISO-8601 字符串，例如 `"2026-09-12T10:30:00"`。

### 关于密码

**任何接口的响应都不包含 `password` 字段。** 返回给前端的是 `UserVO`（只含 `id`、`username`、`nickname`），不是 `User` 实体。

## 二、接口总览

| 序号 | 功能 | 方法 | 路径 |
| --- | --- | --- | --- |
| 1 | 新增用户 | POST | `/user` |
| 2 | 查询单个用户 | GET | `/user/{id}` |
| 3 | 查询用户列表 | GET | `/user/list` |
| 4 | 修改用户 | PUT | `/user` |
| 5 | 删除用户 | DELETE | `/user/{id}` |

## 三、接口详情

### 1. 新增用户

**请求**

```
POST /user
Content-Type: application/json
```

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| username | String | 是 | 用户名，唯一，长度 4–20 |
| password | String | 是 | 密码，长度 6–20，服务端加密后存储 |
| nickname | String | 否 | 昵称，不传则默认为用户名 |

**请求示例**

```json
{
  "username": "zhangsan",
  "password": "123456",
  "nickname": "张三"
}
```

**成功响应**

```json
{
  "code": 200,
  "message": "注册成功",
  "data": {
    "id": 1,
    "username": "zhangsan",
    "nickname": "张三"
  }
}
```

**失败响应**

```json
{
  "code": 400,
  "message": "用户名已存在",
  "data": null
}
```

**服务端要做的事**

- 校验 `username` 是否已存在，存在则返回 400
- 对 `password` 加密后存入，**不能存明文**
- `createTime`、`updateTime` 由服务端生成，不接受前端传入
- 插入成功后返回新用户的 `id`

**实现提示**：组装 `User` 对象后调用 `userMapper.insert(user)`；插入成功后 MP 会自动把数据库生成的自增主键回填到 `user.getId()`，直接取来返回即可。

---

### 2. 查询单个用户

**请求**

```
GET /user/{id}
```

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 用户主键 |

**请求示例**

```
GET /user/1
```

**成功响应**

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1,
    "username": "zhangsan",
    "nickname": "张三"
  }
}
```

**失败响应**（id 不存在时）

```json
{
  "code": 404,
  "message": "用户不存在",
  "data": null
}
```

**实现提示**：`userMapper.selectById(id)`，返回 `null` 说明记录不存在。

---

### 3. 查询用户列表

**请求**

```
GET /user/list
```

无请求参数。

**成功响应**

```json
{
  "code": 200,
  "message": "success",
  "data": [
    {
      "id": 1,
      "username": "zhangsan",
      "nickname": "张三"
    },
    {
      "id": 2,
      "username": "lisi",
      "nickname": "李四"
    }
  ]
}
```

**记录为空时**，`data` 返回空数组 `[]`，不要返回 `null`，前端遍历时不用额外判空。

**实现提示**：`userMapper.selectList(null)`，传 `null` 表示不加任何查询条件。列表数据量大时应该改成分页，这是后面可以补的点。

---

### 4. 修改用户

**请求**

```
PUT /user
Content-Type: application/json
```

**请求参数（Body）**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 要修改的用户主键 |
| nickname | String | 否 | 新昵称 |

**请求示例**

```json
{
  "id": 1,
  "nickname": "张三丰"
}
```

**成功响应**

```json
{
  "code": 200,
  "message": "修改成功",
  "data": null
}
```

**失败响应**（id 不存在时）

```json
{
  "code": 404,
  "message": "用户不存在",
  "data": null
}
```

**服务端要做的事**

- 先确认 id 对应的记录存在，不存在返回 404
- 同时把 `updateTime` 更新为当前时间
- 用户名（`username`）作为登录标识不允许修改；改密码应另开一个独立接口

**实现提示**：`userMapper.updateById(user)`。注意 MP 默认策略是**只更新非 null 字段**，所以只 set 了 `nickname` 和 `updateTime` 的话，其他字段不会被覆盖成 null，这点可以放心。

---

### 5. 删除用户

**请求**

```
DELETE /user/{id}
```

**路径参数**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | Long | 是 | 用户主键 |

**请求示例**

```
DELETE /user/1
```

**成功响应**

```json
{
  "code": 200,
  "message": "删除成功",
  "data": null
}
```

**失败响应**（id 不存在时）

```json
{
  "code": 404,
  "message": "用户不存在",
  "data": null
}
```

**服务端要做的事**

- 先判断记录是否存在。MP 的 `deleteById` 在目标不存在时**不报错、返回 0**，如果直接调，前端会以为删成功了
- 真实项目里删除一般做**逻辑删除**（加 `deleted` 字段标记）而不是物理删除，这块后面可以再优化

**实现提示**：先 `userMapper.selectById(id)` 判断是否为 `null`，再 `userMapper.deleteById(id)`。

## 四、和你当前代码的差异

现有代码里的路径和方法签名跟本文档有几处出入，列出来供对照：

| 位置 | 当前写法 | 本文档写法 | 说明 |
| --- | --- | --- | --- |
| 新增 | `POST /user/register` | `POST /user` | 二选一即可，`register` 也可保留 |
| 删除 | `DELETE /user/delete?id=x` | `DELETE /user/{id}` | id 走路径更符合 REST 风格，类型应为 `Long` |
| 修改 | `PUT /user/update` | `PUT /user` | — |
| 返回值 | `void` | `Result<T>` | 需要新建 `Result` 类 |
| 入参 | `@RequestParam` | `@RequestBody` | JSON 请求体必须用 `@RequestBody` |

如果不想动现有路径，把本文档里的 `POST /user` 换成 `POST /user/register`、`DELETE /user/{id}` 换成对应写法即可，语义不变。

另外有一处现在就能看出来：`UserServiceImpl.delete` 里 `userMapper.selectById(id)` 的返回值没有用上，等于白查一次。要么按上面说的拿它做存在性判断，要么就删掉这行。

## 五、需要新增的类

要让上面的接口跑起来，还差三个类：

| 类名 | 包 | 作用 |
| --- | --- | --- |
| `Result<T>` | `com.jiangpa.common` | 统一响应包装，提供 `success()` 和 `fail(code, message)` 静态方法 |
| `UserVO` | `com.jiangpa.pojo.vo` | 返回给前端的用户视图，只含 id、username、nickname |
| `UserDTO` | `com.jiangpa.pojo.dto` | 接收新增／修改的请求参数 |

`Result` 建议用泛型加静态工厂方法，这样 Controller 里写起来是 `Result.success(data)` / `Result.fail(400, "用户名已存在")`，不用每次手动 new 再 set 三个字段。
