# 角色权限（Role）设计文档

> 项目：Learning（Spring Boot 2.7.18 + MyBatis-Plus + JWT 双 Token + Redis）
> 目标：引入 `role` 字段，补上「纵向越权」这一层防护，修掉 `GET /user/list`、`DELETE /category/{id}` 等全站资产接口的任何登录用户都能操作的缺陷
> 日期：2026-09-18
> 前置阅读：`md/JWT双Token实现设计文档.md`（拦截器链）、`md/逻辑删除设计文档.md`（唯一索引、回归清单）

---

## 一、为什么需要它（这次的触发点）

`role` 不是"加个字段显得完整"，而是要解决一个**已实测的漏洞**：

```
任意登录用户  ->  DELETE /user/{id}      ->  能删掉任何人（已实测 200，受害者被永久锁在门外）
任意登录用户  ->  GET    /user/list      ->  能拉走全站用户列表
任意登录用户  ->  DELETE /category/{id}  ->  能删掉全站分类（分类不属于任何用户）
```

**根因**：现在只有**认证**（你是谁）没有**授权**（你能动谁）。而授权其实有两种，**必须用两套机制**：

| 越权类型 | 例子 | 判定依据 | 机制 |
| --- | --- | --- | --- |
| **水平越权**（同级别之间） | A 删 B 的账号/文章/评论 | 资源**有主** | **归属校验** → 403 |
| **纵向越权**（低权限动高权限资源） | 普通用户删分类、拉用户列表 | 资源**无主（全站资产）** | **角色校验** → 403 |

**归属校验解决不了纵向越权**，因为分类这种东西"不属于任何人" —— 你没法比对一个不存在的所有者。所以必须引入 `role`。

> ⚠️ **`role` 只解决"纵向"。用户模块的归属校验（`DELETE/PUT /user/{id}`）仍然必须单独补** —— 那是水平越权，和角色无关。**两件事都要做，别以为加了 role 就安全了。**

## 二、`role` 放在哪里：三种方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 进 JWT claim**（推荐） | 登录时把 `role` 写进 token | 每个请求**零额外查询**；拦截器直接读 claim | 角色变更后旧 token 里的 role 有**最长 30 分钟的延迟**（access 有效期） |
| B. 每个请求查库 | 拦截器用 `userId` 查 `tb_user.role` | 实时准确 | **每个请求多一次 DB 查询**（本来就为了省 DB 才用 JWT 的，等于把收益还回去） |
| C. Redis 存角色 | 拦截器读 `learning:user:role:{id}` | 比查库快，比 A 实时 | 多一份状态要维护（登录写、改角色清），复杂度最高 |

**选 A**，理由：
1. 与双 Token 体系**天然契合** —— access 本来就只有 30 分钟，role 的陈旧窗口和 token 自身的生命周期一样，不是新增风险；
2. **零额外查询**是 JWT 的核心收益，方案 B 会把它抵消掉；
3. **角色的变更频率极低**（几乎不变），为一个低频事件引入"每请求一次查询"或"多一份 Redis 状态"都不划算。

**A 的代价要写清楚**：把管理员**降级**为普通用户后，他手上那个 access token 在**剩余 30 分钟内仍然是管理员**。解法有两条 ——
- **简单版**（本项目采用）：降级时顺手 `DEL learning:token:refresh:{userId}`，他就**无法续期**，最多 30 分钟后自动失效；
- **严格版**：在 Redis 里放一个"角色版本号"，拦截器比对 token 里的版本 —— 能做到**立即生效**，代价是每个请求多一次 Redis 读（等于把方案 A 的收益还回去一部分）。

> 面试时这是很好的追问点："JWT 里放 role 的代价是什么？" → **陈旧窗口 + 无法立即吊销，需要靠短有效期或版本号兜住**。

## 三、数据库改动

```sql
ALTER TABLE tb_user
  ADD COLUMN role TINYINT NOT NULL DEFAULT 0 COMMENT '0=普通用户 1=管理员' AFTER nickname;
```

**三个要点**：

| 点 | 说明 |
| --- | --- |
| **`NOT NULL DEFAULT 0`** | 和 `deleted` 同一个道理：**默认值必须是"权限最小"**。若允许 NULL，Java 端 `Integer role` 拆箱或比较时容易出问题，且 NULL 不应被理解为"某种更高权限" |
| **默认 0 = 普通用户** | 新注册的人**永远是普通用户**。这是 fail-safe：忘了赋值的后果是"权限不足"，而不是"人人都是管理员" |
| **`TINYINT`** | 与 `deleted` 风格一致。角色数量固定在个位数，不需要 INT |

**已有数据的处理**：`DEFAULT 0` 会让**所有现存用户都变成普通用户**，包括你自己 —— 于是**没有任何人能调管理接口**（包括 `GET /user/list`）。

### 3.1 ⚠️ 第一个管理员怎么来（必须先想清楚）

注册接口**必须**硬编码 `role = 0`，绝不能接受客户端传入的 role。所以第一个管理员只能手工指定：

```sql
-- 把你自己提升为管理员（把 username 换成你的账号）
UPDATE tb_user SET role = 1 WHERE username = 'zhangsan';
-- 确认
SELECT id, username, role FROM tb_user;
```

**这一步不做，加完 role 你会连用户列表都打不开**（403）。建议在 `md/` 里留一条记录说明"初始管理员是手工 SQL 指定的"，将来换机器重建库时不会卡住。

## 四、角色如何随 token 流转（本次改动的关键链路）

**这是最容易漏的地方**：`role` 不只是数据库字段，它必须**进 JWT**，否则拦截器拿不到。

```
登录：
  UserService.authenticate(dto)
    → 返回 UserVO（★ 需要新增 role 字段，否则 AuthController 拿不到它）
  AuthController.login
    → tokenService.issue(userId, username, role)   ★ 方法签名要加参数
  TokenService.issue
    → jwtUtils.generateAccessToken(userId, username, role)   ★ 两个签发方法都要加
  JwtUtils.generateToken（私有）
    → claims.put("role", role)                     ★ 一处改动，两种 token 同时生效
  JwtInterceptor
    → Number role = claims.get("role", Number.class);          ★ 用 Number，不要用 String
      request.setAttribute("role", role == null ? null : role.intValue())
```

**改动清单（按依赖顺序）**：

| # | 文件 | 改什么 | 为什么必须 |
| --- | --- | --- | --- |
| 1 | `tb_user` | 加 `role` 列 | 数据来源 |
| 2 | `pojo/User.java` | 加 `private Integer role;` | MyBatis-Plus 映射（`BeanUtils.copyProperties` 也能带过来） |
| 3 | **`vo/UserVO.java`** | 加 `private Integer role;` | ⭐ **不加这一步 `AuthController` 拿不到角色**，`issue()` 就没东西可传 |
| 4 | `utils/JwtUtils.java` | `generateToken(...)` 加 `role` 参数 + `claims.put("role", role)` | 让角色进 token |
| 5 | `service/TokenService.java` + `impl` | `issue(userId, username, role)`；**`refresh()` 从 claims 取 role 再传回 `issue()`** | 续期后 role 不能丢 —— 从 token 里取，不用查库 |
| 6 | `controller/AuthController.java` | `tokenService.issue(user.getId(), user.getUsername(), user.getRole())` | 把角色接上 |
| 7 | `interceptor/JwtInterceptor.java` | 解析后 `request.setAttribute("role", ...)` | 让后续能读到 |

**关于第 5 步的 `refresh`**：轮换时**从旧 refresh token 的 claims 里取 role**（`claims.get("role", Number.class).intValue()`）再传给 `issue()`。这样续期不需要查库；代价是"降级后 30 分钟内续期仍带旧 role"，用第二节说的"降级时删 refresh key"兜住。

**⚠️ 类型取值必须用 `Number.class`，不能用 `String.class` 或 `Integer.class`**：

| 写法 | 结果 |
| --- | --- |
| `claims.get("role", String.class)` | ❌ **全部业务接口返 401**。jjwt 的类型 getter 是**精确比对**：payload 里 role 是 JSON 数字（`Integer`），要 `String.class` 会抛 `RequiredTypeException`；它继承自 `JwtException`，被拦截器的兜底 catch 吃掉 → 每个合法 token 都被判成"token 无效" |
| `claims.get("role", Integer.class)` | ⚠️ 大多数情况可行，但**不安全**：JSON 数字的反序列化类型**取决于数值大小**（小的变 `Integer`，超范围的变 `Long`），一旦是 `Long` 就同样抛异常 |
| `claims.get("role", Number.class)` | ✅ **唯一安全写法**。`Number` 接受 `Integer`/`Long`，取完再 `.intValue()` |

> 这个坑实测过一次：加了 role 之后**所有带合法 token 的请求全返 401**，排查时很容易误以为是权限拦截器的问题。

## 五、权限校验放在哪一层（⭐ 关键设计决策）

### 5.1 两种做法

| 做法 | 写法 | 问题 |
| --- | --- | --- |
| **拦截器里按路径硬编码** | `if (path.startsWith("/user/list") && role != 1) reject` | ❌ 路径字符串和权限规则**分散在两处**，加接口时极易漏改；改 URL 就要同步改权限代码 |
| **注解声明在方法上**（推荐） | `@RequireRole(ADMIN)` 标在 Controller 方法上 | ✅ 权限规则**和接口定义在同一个文件**，一眼看出谁能调；新增接口时"忘了加注解"= 默认放开（见 5.3 的取舍） |

**选注解**。这也是 Spring Security 那套 `@PreAuthorize` 的思路 —— 用注解表达"谁能调"，而不是用路径匹配表。

### 5.2 放哪个拦截器里：单独一个，还是塞进 `JwtInterceptor`？

| | 塞进 JWT 拦截器 | **单独一个 `AuthorizationInterceptor`** |
| --- | --- | --- |
| 职责 | ❌ 混在一起（验身份 + 判权限） | ✅ 单一职责：一个管"你是谁"，一个管"你能干什么" |
| 读注解 | 要拿 `handler` 强转 `HandlerMethod` | 同样要，但语义清晰 |
| 谁需要它 | — | **只有已登录接口**，所以它天然排在 JWT 之后 |

**选单独一个**，注册在 `JwtInterceptor` 之后：

```java
// WebMvcConfig —— 顺序即优先级
registry.addInterceptor(jwtInterceptor)            // ① 验 token、挂 userId/role，排除 /auth/**
        .addPathPatterns("/**")
        .excludePathPatterns("/auth/**", "/error");

registry.addInterceptor(authorizationInterceptor)  // ② 读 @RequireRole，比对 role
        .addPathPatterns("/**")
        .excludePathPatterns("/auth/**", "/error");
```

> **接口限流文档里注册了第三个拦截器**（限流不排除 `/auth/**`）。三个拦截器的顺序建议：**JWT → 授权 → 限流**。
> 理由：先确认身份（否则无 userId 可限）、再判权限（**没权限的请求不该消耗限流额度**，也不该让无权限请求把管理员的额度算进去）、最后限流。

### 5.3 取舍：忘了加注解会怎样

| 默认策略 | 忘记标注的后果 | 安全姿态 |
| --- | --- | --- |
| **默认放开**（本项目） | 新接口**任何登录用户都能调** | ⚠️ 偏"方便"，靠 code review 兜 |
| 默认拒绝（白名单放行） | 新接口**谁也调不了**，必须显式加注解 | ✅ 更安全，但开发体验差、容易上线才发现把功能锁死 |

**本项目选"默认放开"**，理由：接口少、有 code review、且"忘记加注解"会在测试时立刻暴露（普通账号一测就能调）。
**但必须把这个取舍写在文档里** —— 面试官问"你的权限框架默认是拒绝还是放行"，要答得出**自己选了什么、为什么、代价是什么**。生产上更常见的是"默认拒绝 + 显式白名单"。

### 5.4 拦截器实现要点（自己写，结构如下）

```
preHandle：
  ① handler 不是 HandlerMethod（静态资源、/error 转发）→ return true
  ② 方法上没有 @RequireRole → return true（默认放开）
  ③ 从 request attribute 取 role（由 JwtInterceptor 挂上）
       ★ 取不到 → 说明这个接口没走 JWT 鉴权 → 必须拒绝（不能放行）
  ④ role 与注解要求比对，不满足 → 写 403 响应体，return false
  ⑤ 满足 → return true
```

**③ 是关键防线**：如果某个接口被错误地加进了 JWT 放行名单，`role` 就是 null —— 此时**必须拒绝**，绝不能因为"读不到角色"就当成合法请求放行。这和 `isRevoked` 的 fail-closed 是同一条原则。

**又是那个坑**：`preHandle` 返回 false **不会自动生成响应体**，必须自己写（照抄 `JwtInterceptor.writeUnauthorized`，改成 403）。

## 六、哪些接口需要什么权限（完整矩阵）

把**三类校验**一起列出来，避免"加了 role 就以为安全了"：

| 接口 | 校验类型 | 规则 |
| --- | --- | --- |
| `POST /auth/register`、`/auth/login`、`/auth/refresh`、`/auth/logout` | 无（放行） | 登录接口本来就要匿名可访问 |
| `DELETE /user/{id}` | **归属** | 「自己 **或** 管理员」；⚠️ **不要**再叠加 `@RequireRole`（会先按角色拦掉普通用户，"删自己"分支永远走不到） |
| `PUT /user/{id}` | **归属** | 只能改自己的昵称（管理员也不能改别人的 —— 昵称属个人） |
| `PUT /user/role`（**新增**） | **角色** | 仅管理员；**角色值放在请求体**（`{id, role}`），不是路径 |
| `GET /user/{id}` | **归属 ∪ 角色** | 「自己 **或** 管理员」—— 普通用户要能看自己的个人中心 |
| `GET /user/list` | **角色** | ⭐ 仅管理员 —— 这就是本次要修的那条 |
| `POST/PUT/DELETE /category/**` | **角色** | ⭐ 仅管理员（分类是全站资产） |
| `GET /category/list` | 无（登录即可） | 只读、无敏感信息 |
| `POST/PUT/DELETE /article/**` | **归属** | 作者本人（已实现） |
| `GET /article/**` | 无（登录即可） | — |
| `POST /comment` | 无（登录即可） | — |
| `DELETE /comment/{id}` | **归属** | 作者本人（已实现） |
| `GET /comment/list` | 无（登录即可） | — |

**已定的产品决策（2026-09-18 敲定）**：

| 问题 | 决定 | 落地位置 |
| --- | --- | --- |
| `DELETE /user/{id}` 谁能删 | **「自己 或 管理员」** | `UserServiceImpl.delete` + Controller **不加** `@RequireRole` |
| `GET /user/{id}` 谁能看 | **「自己 或 管理员」** | `UserServiceImpl.selectUser` + Controller **不加** `@RequireRole` |
| `PUT /user/{id}` 谁能改 | **只有本人**（管理员也不行） | `UserServiceImpl.update` 只判归属 |
| `GET /user/list` | **仅管理员** | `@RequireRole(1)` |
| 分类增删改 | **仅管理员** | `@RequireRole(1)` × 3 |

## 七、改角色接口（实际实现）

```java
// PUT /user/role          仅管理员（@RequireRole(1)）
// body: { "id": 18, "role": 1 }     role: 0=降级为普通用户, 1=升级为管理员
@PutMapping("/role")
public Result<?> updateRole(@Valid @RequestBody UserRoleUpdateDTO userRoleUpdateDTO) {
    userService.updateRole(userRoleUpdateDTO);
    return Result.success();
}
```

**DTO**（`dto/UserRoleUpdateDTO.java`）：

```java
@Data
public class UserRoleUpdateDTO {
    @NotNull(message = "用户id不能为空")
    private Long id;

    @NotNull(message = "权限设定不能为空！")
    @Min(value = 0, message = "权限值只能是 0(降级) 或 1(升级)")
    @Max(value = 1, message = "权限值只能是 0(降级) 或 1(升级)")
    private Integer role;
}
```

> **设计变更记录**：初版设计是 `PUT /user/{id}/role`（id 在路径、body 只有 role）。实现时改成了 **`PUT /user/role`（id 也放 body）**，理由是"统一在 DTO 里声明两个字段、校验规则集中在一处"。已按实现同步本文档。

### 7.1 五个必须点

1. **绝不能复用 `UserUpdateDTO`**。角色改动必须是**独立接口 + 独立 DTO**，且只有带 `@RequireRole(1)` 的管理员能调。如果把它塞进现有的 `PUT /user/{id}`，那就回到了"任何登录用户都能把自己提成管理员"——**比原来的漏洞更严重**（原来只是删数据，这个是拿下整个系统）；
2. **`role` 取值必须校验 0/1**。用 `@Min(0) + @Max(1)`，**不要用 `@Size`**（`@Size` 是"元素/字符个数"，标在 `Integer` 上会让校验器抛 `UnexpectedTypeException`，见踩坑清单）；
3. **⚠️ 必须加 `@Valid`**。约束注解只是元数据，**漏写 `@Valid` 会让整组约束静默失效** —— 越界值（`role=9`、`role=-1`）和缺失字段全部放行、接口照常返回 200，而且 DB 真的被写脏。**这一条实际踩过**（见第十三节）；
4. **不能降级最后一个管理员**：如果允许把最后一个管理员降级，系统会**永久失去管理能力**（只能再去数据库手工改回来）。守卫要判断"**目标之外还有没有管理员**"（`.ne(User::getId, id)`），并且**只在该操作是"把管理员降为 0"时才检查**；
5. **角色变更后必须作废旧凭证**（见 7.2）。

### 7.2 ⚠️ 改角色后要清 refresh key（位置很关键）

角色写在 JWT claim 里，而 `refresh` 是**从旧 token 的 claims 取 role 再签发新 token**（零查询的代价）。所以**只要旧 refresh token 还能用，旧角色就能被无限续期** —— 不清理的话，"降级"等于没降。

**实现要点：清 key 必须无条件执行，且放在守卫之后、落库之后**：

```java
Integer role = dto.getRole();

// ① 守卫放最前：否则会被抛异常跳过后面的清理
if (user.getRole() != null && user.getRole().equals(1) && role != null && role == 0) {
    Long count = userMapper.selectCount(new LambdaQueryWrapper<User>()
            .eq(User::getRole, 1).ne(User::getId, dto.getId()));
    if (count == 0) throw new BusinessException(403, "无法降级最后一位管理员");
}

// ② 落库
user.setRole(role);
userMapper.updateById(user);

// ③ 无条件作废旧凭证 —— 不能放在 if(target 是管理员) 里面！
try {
    stringRedisTemplate.delete(CacheKeys.tokenRefresh(user.getId()));
} catch (Exception e) {
    log.warn("删除 refresh key 失败，不影响本次返回", e);
}
```

**两个曾经写错的位置**（都实测出来了）：

| 写错的方式 | 后果 |
| --- | --- |
| 清 key 放在 `if (target 当前是管理员)` **里面** | **降级普通用户时根本不执行** → 旧 refresh 继续换新 token，把旧 role 一起带过去 |
| 清 key 放在守卫**之后**（`throw` 之后） | 降级最后一个管理员时会先抛 403，**清理语句永远到不了** |

> **为什么"提升"也要清**：提升后旧 token 里 role 仍是 0，用户拿着它访问不了管理接口。清掉让他重新登录，**规则统一、行为可预期**（而不是"降级清、提升不清"这种不一致）。

**已知残留代价**：access token 无状态，改角色后**它最多还能用 30 分钟**（无法立即吊销）。清 refresh key 保证的是"**无法续期**"，不是"立即失效"。要立即失效需要引入"角色版本号"比对。

## 八、验收清单

### 8.1 普通用户（用普通账号的 token）

```
① GET  /user/list            -> 403（★ 本次要修的主目标）
② GET  /user/{otherId}       -> 403
③ GET  /user/{自己的id}       -> 200（别把自己也挡了）
④ DELETE /user/{otherId}     -> 403（这是归属校验，和 role 无关）
⑤ DELETE /user/{自己的id}     -> 200
⑥ POST/PUT/DELETE /category  -> 403（★ 本次要修的第二个目标）
⑦ PUT  /user/role 改自己      -> 403（且不能把自己提权！★ 最关键的一条）
⑧ DELETE /comment/{别人的}    -> 403（回归：原有归属校验不能被改坏）
⑨ PUT/DELETE /article/{别人的} -> 403（回归同上）
⑩ GET  /article/list、/category/list、/comment/list -> 200（回归：只读接口不能被误锁）
```

**第 ⑦ 条是重中之重**：测"普通用户试图把自己 role 改成 1"，期望 **403**。如果这里返回 200，说明提权漏洞存在 —— 比原来的删数据漏洞严重得多。

**校验用例（`@Valid` 回归，实测过）**：

```
{id:18, role:9}   -> 400「权限值只能是 0(降级) 或 1(升级)」+ DB 不变
{id:18, role:-1}  -> 400 + DB 不变
{id:18}           -> 400「权限设定不能为空！」
{role:1}          -> 400「用户id不能为空」
{id:999999,role:1}-> 404「用户不存在！」
```

### 8.2 管理员（用管理员 token）

```
① GET  /user/list            -> 200
② DELETE /category/{id}      -> 200
③ PUT  /user/role  改别人     -> 200
④ 提升路径的端到端验证（★ 实测过）：
     提升 → 【重新登录】→ 新 token 里 role=1 → 调 GET /user/list -> 200
     （只验证"DB 变了"不够，要验证"新凭证真的能拿到权限"）
⑤ 降级路径：
     - 被降级者的旧 refreshToken -> 401（★ 证明 refresh key 被清了）
     - 他的旧 access token 在剩余 30 分钟内仍是旧角色（已知代价）
     - 他下一次登录后 token 里是新角色
⑥ 最后一个管理员守卫（两个方向都要测）：
     - 只剩 1 个管理员时降级它 -> 403
     - 有 2 个管理员时降级其中一个 -> 200（不能把它一起锁死）
```


### 8.3 token 链路（最容易漏的回归）

```
① 登录后把 accessToken 贴到 jwt.io 解码 -> payload 里必须有 "role"
② 管理员登录 → 用他的 token 调 /user/list -> 200
③ 【关键】用管理员 token 调 /auth/refresh 换新 token → 新 token 里 role 仍是 1
     → 验证 refresh 把 role 从 claims 带过去了（漏了的话管理员续期后变普通用户）
④ 普通用户登录 → token 里 role=0 → 调管理接口 403
```

### 8.4 全量回归

本次改动了 **JWT 签发链路 + 新增拦截器**，影响所有接口。必须回归 16 个接口（用户 4 + 文章 5 + 分类 4 + 评论 3），确认：
- 管理员能调全部；
- 普通用户**读接口**（文章详情/列表、评论列表、分类列表）**仍然正常**（别把只读接口也锁了）；
- 双账号的 403 分支仍然正确。

## 十、踩坑清单

| # | 坑 | 后果 | 避免 |
| --- | --- | --- | --- |
| 1 | **`UserVO` 忘了加 `role`** | `AuthController` 拿不到角色，`issue()` 传 null → token 里没有 role → 拦截器判定失败 | 第三节改动清单第 3 行 |
| 2 | **`refresh()` 没把 role 带过去** | 管理员续期一次就**变成普通用户**，30 分钟后管理功能全部 403 | 从旧 token 的 claims 取 role 再传 `issue()` |
| 3 | **`role` 允许客户端传入**（注册/更新 DTO 里有 role 字段） | **任何人注册成管理员**或**自己提权** —— 比原漏洞严重得多 | `role` 永不进请求 DTO；注册硬编码 0；改角色走独立接口 + `@RequireRole(ADMIN)` |
| 4 | 加完 role 没手工指定第一个管理员 | **没人能调管理接口**，用户列表自己也打不开 | 先跑第三节的 `UPDATE ... SET role=1` |
| 5 | 注册默认给了 `role=1` | 人人都是管理员，等于没有权限系统 | 默认 **0** |
| 6 | 拦截器里读不到 role 就放行 | 如果接口被误加进放行名单，**权限校验被静默绕过** | 读不到 role → **拒绝**（同 fail-closed） |
| 7 | 用路径硬编码判权限 | 改 URL / 加接口时权限规则不同步，产生漏网接口 | 用注解，权限和接口定义在同一个文件 |
| 8 | 授权拦截器注册在 JWT **之前** | `role` attribute 还没挂上，全部请求判为无权限（或全部放行） | 顺序：JWT → 授权 → 限流 |
| 9 | `preHandle` 返 false 不写响应体 | 前端收到内容为空的 200，既没权限也不知道为什么 | 照抄 `writeUnauthorized` |
| 10 | 以为加了 role 就等于修了越权 | `DELETE /user/{id}` 仍然是水平越权（A 能删 B） | 归属校验和角色校验**分别做**（矩阵见第六节） |
| 11 | 管理员降级后旧 token 仍有效 | 30 分钟的管理员窗口 | 降级时删他的 refresh key；或引入角色版本号 |
| 12 | 允许把最后一个管理员降级 | 系统永久失去管理能力，只能改库恢复 | 加"不能降级最后一个管理员"的保护 |
| 13 | 把 `role` 放进 `UserVO` 后**接口把它返回给前端** | 泄露内部权限模型（影响不大，但没必要） | 前端不需要知道 role；要么用单独的 VO，要么接受这点轻微泄露 |
| 14 | **⚠️ 漏写 `@Valid`** | **整组约束静默失效**：`role=9` / `role=-1` / 缺字段全部放行并返回 200，DB 真被写脏。**且不报错、日志干净** | `@RequestBody` 参数上必须写 `@Valid`（实测踩过，见第十三节） |
| 15 | **`@Size` 标在 `Integer` 上** | 校验器抛 `UnexpectedTypeException` → 掉到兜底 → **连 `@NotNull` 一起崩，返 500** | 数值范围用 `@Min`/`@Max`。**"校验注解返 500"基本可断定是注解用错了类型** |
| 16 | **`claims.get("role", String.class)`** | jjwt 精确类型比对，JSON 数字取 String 抛 `RequiredTypeException`（继承 `JwtException`）→ 被拦截器兜底吃掉 → **所有合法 token 的请求全返 401** | 用 `Number.class` 再 `.intValue()`；也别用 `Integer.class`（数值大时会变 `Long`） |
| 17 | **改角色后清 refresh key 的位置错了** | 放在 `if (target 是管理员)` 里 → 降级普通用户时不执行；放在守卫 `throw` 之后 → 永远到不了。**结果旧 refresh 继续换新 token 并继承旧 role，降级形同虚设** | 清 key **无条件执行**、放在守卫之后 + `updateById` 之后；提升路径也一起清 |
| 18 | **"最后一个管理员"判断没排除目标自己** | `count <= 1` 用全表计数，两个管理员时降级其中一个也会被拦（或反向算错） | 计数要 `.ne(User::getId, id)`，且只在"把管理员降为 0"时检查 |

## 十一、面试怎么答

| 问题 | 答案要点 |
| --- | --- |
| ⭐ **认证和授权有什么区别？** | 认证 = 你是谁（JWT 验签）；授权 = 你能干什么。**JWT 只解决认证**。拦截器验完 token 只证明"这是个合法用户"，不代表他有权操作这个资源 |
| ⭐ **水平越权和纵向越权？** | 水平 = 同级别用户之间互操作（A 删 B 的文章/账号）；纵向 = 低权限用户操作高权限资源（普通用户删分类、拉用户列表）。**两者要用不同机制**：归属校验 vs 角色校验 |
| **为什么归属校验解决不了纵向越权？** | 因为纵向越权的目标资源**没有主**（分类、用户列表是全站资产），你没法比对"所有者"。所以必须引入角色 |
| **role 放 JWT 还是查库？** | 放 JWT：零额外查询，但角色变更最长 30 分钟才生效（陈旧窗口）。查库：实时但每请求一次查询，抵消了 JWT 的意义。**角色是低频变更，选 JWT + 靠短有效期兜住**，严格场景加"角色版本号" |
| **权限校验放拦截器还是注解？** | 注解（`@RequireRole`）—— 权限规则和接口定义在同一个文件，改 URL 不会不同步。路径硬编码会把规则分散到两处，加接口容易漏 |
| **你的权限框架默认放行还是拒绝？** | 本项目默认放行（忘记加注解 = 任何登录用户可调），靠 code review + 测试兜；**生产上更常见的是默认拒绝 + 显式白名单**。**关键是能说清自己选了哪个、代价是什么** |
| **怎么防"普通用户把自己提成管理员"？** | `role` 绝不进请求 DTO；注册硬编码 `role=0`；改角色走独立接口且要求 `@RequireRole(ADMIN)`。**这是权限系统里最危险的一条**：一个字段绑定错误 = 整套权限失效 |
| **管理员被降级后旧 token 还能用吗？** | 能，直到 access 过期（最长 30 分钟）。这是"role 放 JWT"的固有代价，用"降级时删 refresh key"限制续期，或用角色版本号做到立即失效 |
| **拦截器里读不到角色怎么办？** | **拒绝**。读不到说明这个请求没经过鉴权（可能被误加进放行名单），放行就等于权限校验被静默绕过 —— 和黑名单的 fail-closed 同一条原则 |

### 13.2 只有测试才能暴露的四个缺陷（按发现顺序）

**① `claims.get("role", String.class)` → 所有业务接口返 401**

写入端 `claims.put("role", role)` 是 `Integer`，payload 里是 JSON 数字；jjwt 的类型 getter 精确比对，要 `String.class` 抛 `RequiredTypeException`，它**继承自 `JwtException`**，被拦截器兜底 catch 吃掉 → 每个合法 token 都判成"token 无效"。
**教训**：改 JWT payload 时，**取值类型必须和写入类型对齐**，用 `Number.class` 最稳。

**② 权限判断写成 `!A || !B` → "自己看不了自己"**

`selectUser` / `delete` 里写成 `!Objects.equals(id, userId) || !Objects.equals(role, 1)`，等价于 `!(A && B)` = "必须同时是自己**且**是管理员"。
实测：普通用户查自己的资料 → 403；管理员查别人 → 403。
**为什么测试差点漏掉**：写反后"普通用户查别人 → 403"这条**恰好是对的**，看起来像已经生效。
**教训**：权限用例必须**成对测**（该拒的拒 + 该放的放）。

**③ `@Valid` 漏写 → 校验注解全是摆设**

`updateRole(@RequestBody ...)` 少了 `@Valid`。实测：`{role:9}` → **200 且 DB 写成 9**；`{role:-1}` → **200 且写成 -1**；缺 `role` → **200 且写成 NULL**。
因为 `role` 决定权限、而判定是 `role != 1`，**非法值同样能通过管理员校验** → "隐形管理员"。
**教训**：`@Valid` 是开关，约束注解只是元数据。**发一个越界值验证是否被拒**是必备动作。

**④ 改角色后清 refresh key 的位置错了 → 降级形同虚设**

清 key 写在 `if (target 当前是管理员)` 内部。实测：**降级一个普通用户后，用降级前的 refreshToken 仍能换出新 token**，而且新 token 的 payload 里 `role` 是被污染的 `-1` —— 因为 `refresh` 是从旧 token 的 claims 取 role。
**教训**：作废旧凭证这个动作属于"**角色发生了变更**"这件事，不属于"目标是管理员"这个条件；而且**不能放在 `throw` 之后**（永远到不了）。
