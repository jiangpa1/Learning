## 〇、当前项目状态（写本文档时的代码现状）

限流是**第三个**加进拦截器链的组件。动手前先对齐现状，否则第六节的顺序会写错：

| 组件 | 类 | 放行规则 | 职责 |
| --- | --- | --- | --- |
| ① JWT 拦截器 | `interceptor/JwtInterceptor` | 排除 `/auth/**`、`/error` | 验签 + 验期 + 校验 `type=access` + 查黑名单 → 挂 `userId` / `username` / **`role`** |
| ② 授权拦截器 | `interceptor/AuthorizationInterceptor` | 排除 `/auth/**`、`/error` | 读方法上的 `@RequireRole` → 比对 `role`；读不到 role 直接拒绝（fail-closed） |
| ③ **限流拦截器（本文档）** | 待新增 | **只排除 `/error`；不排除 `/auth/**`（登录/注册必须限流）** | 按维度计数 → 超限返 `code=429` |

**已实现的相关能力**（限流可以复用）：
- `request` attribute 里已经有 **`userId`** 和 **`role`**（由 ① 挂上），所以限流既能按用户限、也能按角色区分阈值；
- `CacheKeys` 已集中管理 `learning:` 前缀（限流 key 照此新增）；
- `ArticleServiceImpl` 里已有 `DefaultRedisScript` 的用法（解锁脚本），Lua 写法可直接照抄；
- 降级策略已有三处样本（缓存 fail-open、黑名单 fail-closed），本文档的限流是**第四个、也是第三个 fail-open**。

## 一、结论先行

1. **算法选「固定窗口」起步，但必须知道它的边界双倍问题**；想一步到位就上**滑动窗口（ZSET + Lua）**，这是本项目推荐版本。
2. **限流是性能层，Redis 挂了要 fail-open（放行）** —— 和 `JwtInterceptor` 查黑名单的 fail-closed **正好相反**，同一条请求链上两种策略并存，这是本设计最值钱的面试点。
3. **限流拦截器必须注册在 JWT 与授权拦截器之后**（`JWT → 授权 → 限流`）：拿不到 `userId` 就只能按 IP 限；排在授权之前还会让**没权限的请求白白消耗限流额度**。
4. **限流返回独立业务码（不是 401、不是 429 直返）**：本项目 HTTP 恒 200、业务码在 body 里，所以用 `code=429`，并且它**绝不能被前端当成"该跳登录页"**。
5. `preHandle` 返回 false **不会自动生成响应体** —— 必须像 `writeUnauthorized` / `writeForbidden` 那样自己往 response 写，否则前端收到内容为空的 200。

## 二、为什么要限流（先想清楚保护什么）

限流不是"加上就安全"，**先回答"要保护什么、被谁打"**，方案才有依据：

| 攻击/风险 | 特征 | 该在哪个维度限 |
| --- | --- | --- |
| **撞库 / 暴力破解密码** | 同一 IP 高频打 `/auth/login`，换用户名 | **IP + 接口**，且 login 要单独设最严的阈值 |
| **恶意刷接口** | 单个已登录用户高频调某个接口 | **userId + 接口** |
| **爬虫抓文章** | 未登录、大量 IP、抓 `/article/{id}` | **IP**（未登录时无 userId） |
| **写接口灌水** | 高频发文章/评论 | **userId + 接口**，写入类阈值要低 |
| **资源耗尽** | 慢接口（含 DB 查询的列表/详情）被并发打满 | **接口级总闸** + 连接池保护 |

**⚠️ 限流的两条铁律**：

1. **限流不能替代鉴权。** 它是"减少损害"，不是"阻止访问"。撞库限流只是拖慢，真正的防线是 `BCrypt` + 密码强度 + 失败锁定；
2. **阈值定错比不限流更糟。** 阈值定太紧 → 正常用户被挡（尤其移动端网络抖动会重试）；定太松 → 形同虚设。**阈值应该来自真实流量观测，不是拍脑袋**（本项目没有生产流量，所以阈值只是"演示值"，文档里要写清这一点）。

## 三、四种算法：差别到底在哪

### 3.1 固定窗口（Fixed Window）—— 最简单，但有硬伤

```
key = learning:limit:{标识}:{窗口号}      窗口号 = 当前时间 / 窗口大小
INCR key
if (首次) EXPIRE key 窗口大小
if (count > 阈值) 拒绝
```

**为什么它不够**：

> 阈值 100/分钟。用户在 **12:00:59** 打满 100 次，**12:01:00** 窗口重置又能打 100 次。
> **跨越窗口边界的 2 秒内，实际通过了 200 次** —— 是阈值的两倍。这就是**临界问题（boundary burst）**。

**它并非不能用**：单机、阈值宽松、只是"防呆"的场景完全够。**但面试问"固定窗口有什么问题"，答不出这个双倍问题就露馅。**

### 3.2 滑动窗口（Sliding Window）—— 本项目推荐 ⭐

不按"整点窗口"计数，而是**记录每次请求的时间戳，只统计"最近 N 秒"内的请求数**：

```
ZREMRANGEBYSCORE key 0 (now - window)   ← 先清掉窗口外的旧记录
count = ZCARD key                        ← 剩下的就是窗口内的请求数
if count >= 阈值: 拒绝
ZADD key now now                         ← 记录本次请求
EXPIRE key window
```

**好处**：
- **没有临界双倍问题** —— 窗口是"滑动的"，任意时刻看的都是"过去 N 秒"，边界是连续的；
- 精度可调（按毫秒存，比固定窗口精确）。

**代价**：
- **内存是固定窗口的数倍**：每个请求都要在 ZSET 里留一条记录（固定窗口只存一个计数器）。阈值 100/分钟 → 最坏 100 个成员；
- `ZREMRANGEBYSCORE` 是 O(log N + M)，比 `INCR` 重。

### 3.3 令牌桶（Token Bucket）—— 应对突发流量

桶里按固定速率补充令牌，请求来了取一个，取不到就拒绝：

```
令牌数 = min(容量, 上次剩余 + (now - 上次时间) * 速率)
if 令牌数 >= 1: 扣一个, 放行
else: 拒绝
```

**特点**：
- **允许突发**：桶里攒着令牌时，可以一瞬间通过"容量"个请求，之后被速率限制住。适合"平时很闲、偶尔爆发"的接口（如文章详情被分享后短时涌入）；
- 内存 O(1)，比滑动窗口省；
- 实现比滑动窗口复杂（要存 `上次时间` + `剩余令牌`，且必须原子）。

### 3.4 漏桶与队列 —— 本项目不用

漏桶是"请求以恒定速率流出"，超出部分排队或丢弃。**排队会占住服务器线程**（本项目用 Tomcat 线程池，排队 = 线程被占用 = 更早被拖垮），所以**不引入**。工业界用它的场景通常配合网关（如 Nginx `limit_req`）。

### 3.5 选型结论

| 方案 | 临界双倍 | 内存 | 实现难度 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | ❌ 有 | 极低 | ★ | 防呆、阈值宽松、单机 |
| **滑动窗口** | ✅ 无 | 中（数倍） | ★★★ | **本项目推荐**：通用、精确、能讲清原理 |
| 令牌桶 | ✅ 无 | 低 | ★★★★ | 需要允许突发的接口 |
| 漏桶/队列 | ✅ 无 | 中 | ★★★★ | ❌ 线程会排队，本项目不用 |

> **面试话术**："我选了滑动窗口 —— 固定窗口便宜但有临界双倍问题，滑动窗口用 ZSET 存时间戳消除了它，代价是内存换精度；如果场景是'平时很闲、偶尔爆发'，令牌桶更合适。"

## 四、Redis 数据结构

### 4.1 Key 设计

```java
// 加到 CacheKeys
public static String rateLimit(String dimension, String id) {
    return PREFIX + "limit:" + dimension + ":" + id;
}
```

| 维度 | key 示例 | 说明 |
| --- | --- | --- |
| 按用户 + 接口 | `learning:limit:user:17:/article` | 已登录用户，最精确 |
| 按 IP + 接口 | `learning:limit:ip:192.168.1.5:/auth/login` | 未登录接口（login/register） |
| 接口总闸 | `learning:limit:api:/article` | 全局兜底，防单接口打满 |

**三个设计要点**：

1. **key 必须带 `learning:` 前缀** —— 你的虚拟机是多项目共用（见 `Redis缓存设计文档.md`）；
2. **key 里必须带接口路径**，否则"登录限 5 次/分钟"会把用户访问文章的次数一起算进去；
3. **ZSET 一定要设 `EXPIRE`**，否则没人访问的 key 永远留在 Redis（和 `views` key 不同，那个是设计上就不设 TTL 的，限流 key 必须设）。

### 4.2 ⚠️ 为什么必须用 Lua（原子性）

**不用 Lua 的写法有竞态**：

```
① ZREMRANGEBYSCORE   清旧记录
② ZCARD              数一下          ← 两个请求可能都读到 99
③ ZADD               记录本次        ← 都判断"没超"，都写入 → 超限
```

第 ② 步和第 ③ 步之间**不是原子的**，并发下会**放行超过阈值的请求**（和第 3.1 的固定窗口"读-改-写"一样，都是 check-then-act 竞态）。

**修法：把"清理 + 计数 + 写入"打包成一个 Lua 脚本**，Redis 单线程执行脚本期间不会插入其他命令：

```lua
-- KEYS[1] = 限流 key
-- ARGV[1] = 当前时间戳(毫秒)   ARGV[2] = 窗口大小(毫秒)   ARGV[3] = 阈值
local now    = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local limit  = tonumber(ARGV[3])

-- 清掉窗口外的旧记录
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)

-- 数窗口内的请求数
local count = redis.call('ZCARD', KEYS[1])

if count >= limit then
    return 0            -- 超限，拒绝
end

-- 放行：记录本次请求（member 用 now，重复也没关系）
redis.call('ZADD', KEYS[1], now, now)
redis.call('PEXPIRE', KEYS[1], window)   -- ★ 必须续期，否则冷 key 永久残留
return 1
```

**Lua 里的三个坑**：

| 坑 | 后果 |
| --- | --- |
| **时间不要用 Redis 的 `TIME` 命令，由 Java 端传进来** | 脚本里取时间是可行的，但会让时间点取决于脚本执行时机、**脚本无法脱机测试**，也不好写单元测试。**显式传参**（`ARGV[1]`）更清晰也更可测 |
| **`ZADD` 的 member 用 `now`**，同一毫秒两个请求会**覆盖**成一条 | 计数偏少 → 限流失效。多线程高并发下要拼随机后缀（本项目流量下可接受，但要写在文档里） |
| **忘了 `EXPIRE`** | 冷 key 永久占用内存 |

> `StringRedisTemplate.execute(script, keys, args...)` 你已经在 `ArticleServiceImpl` 的解锁脚本（`UNLOCK_SCRIPT`）里用过同一套写法，可以照抄结构。

## 五、限流维度与 key 的取法

### 5.1 维度选择

| 接口类型 | 推荐维度 | 理由 |
| --- | --- | --- |
| `/auth/login`、`/auth/register` | **IP**（未登录，无 userId） | 防撞库。**这是最需要限流的两个接口** |
| 写接口（发文章/评论/建分类） | **userId** | 防灌水；userId 来自 JWT，无法伪造 |
| 读接口（文章详情/列表） | **IP 或 userId**，阈值放宽 | 正常用户会连续翻页，卡太死体验差 |
| 高风险接口（`/auth/refresh`） | **IP** | 防被人拿泄露的 refresh token 狂刷 |

### 5.2 ⚠️ IP 怎么取才不是"假限流"

**这是最容易写错的地方**：`request.getRemoteAddr()` 拿到的是**直连的上一跳地址**。如果部署在 Nginx / 网关后面，它永远是**网关的 IP** → **所有用户共用一个限流额度** → 第一个人打满，全站被限。

正确顺序：

```java
// 1) 反向代理会把自己的地址塞进 X-Forwarded-For（最左是真实客户端，但可伪造）
// 2) 只有当"直连来源"是可信代理时才能采信 XFF，否则攻击者自己伪造一个就绕过限流
String ip = request.getHeader("X-Forwarded-For");   // 取第一个非 unknown 的值
if (ip == null || ip.isEmpty()) ip = request.getRemoteAddr();
```

**安全要点**：`X-Forwarded-For` **可以伪造**。所以：
- 本项目**本地直连（无网关）**，用 `getRemoteAddr()` 就是对的，**不要无脑上 XFF**（上了反而给攻击者一个"改个 header 就绕过限流"的洞）；
- 生产上学 Nginx 配 `set_real_ip_from` 只信任自己的网关，或直接用 `X-Real-IP` 并把网关设为唯一可信源。

> 面试追问"限流被绕过怎么办"，这就是标准答案：**限流依赖的标识必须不可伪造** —— userId 来自签名 JWT（可信），IP 来自 TCP 连接（可信），但 `X-Forwarded-For` 来自客户端（不可信）。

## 六、拦截器实现与注册顺序

### 6.1 为什么要独立一个拦截器

**不要塞进 `JwtInterceptor`**。职责不同（一个验身份、一个控频率），塞一起会让"鉴权"这个单一职责被污染，而且限流要能作用在**放行名单**上（`/auth/login` 必须限流，但它不走 JWT 鉴权）。

**也不要塞进 `AuthorizationInterceptor`**。那个拦截器是**安全层**（读不到角色要 fail-closed），而限流是**性能层**（Redis 挂了要 fail-open）—— **同一个类里放两种相反的降级策略，将来改一处必然踩另一处**。三个拦截器各管一段，边界才清楚：

```
JwtInterceptor          你是谁        → 安全层，fail-closed
AuthorizationInterceptor 你能干什么    → 安全层，fail-closed
RateLimitInterceptor     让不让你干    → 性能层，fail-open   ← 本文档
```


### 6.2 注册顺序 ⚠️ 顺序错了 userId 拿不到

`WebMvcConfig` 里现在有**两个**拦截器（顺序即优先级）：

```java
registry.addInterceptor(jwtInterceptor)              // ① 验签 + 挂 userId/role
        .addPathPatterns("/**")
        .excludePathPatterns("/auth/**", "/error");

registry.addInterceptor(authorizationInterceptor)    // ② 读 @RequireRole 判权限
        .addPathPatterns("/**")
        .excludePathPatterns("/auth/**", "/error");
```

**限流加在最后**：

```java
registry.addInterceptor(rateLimitInterceptor)        // ③ 限流（此时 userId 一定已挂上）
        .addPathPatterns("/**")
        .excludePathPatterns("/error");              // ★ 不过滤 /auth/**，登录必须限流
```

**三个关键点**：

| 点 | 说明 |
| --- | --- |
| **限流不能排除 `/auth/**`** | 登录/注册正是最需要限流的接口。排除掉等于把门敞开（注意它和 ①② 的放行规则**故意不同**，copy 时最容易顺手抄错） |
| **排在 ① 之后** | 否则 `userId` / `role` 还没挂上，只能按 IP 限 |
| **⭐ 排在 ② 之后** | **没权限的请求不该消耗限流额度**。若限流在前：一个普通用户狂刷 `GET /user/list`，每次都先被限流计数（可能把自己的额度耗尽），然后才被授权拦成 403；更糟的是**攻击者可以用"必然 403 的请求"去消耗目标用户/IP 的限流额度**（相当于一个廉价的拒绝服务放大器） |

> **一句话记住顺序**：`先确认你是谁（JWT）→ 再确认你能不能干（授权）→ 最后才决定让不让你干（限流）`。
> 这也回答了"限流到底该拦什么"：**只拦合法的请求**。非法请求在授权那层就已经被拒了，不该占用限流资源。

> 补充：也可以用 `@Order` 或 `registry.addInterceptor(...).order(n)` 显式指定顺序，比依赖注册先后更不容易被后人改错（现在有三个拦截器了，靠"注册先后"来保证顺序已经开始脆弱）。


### 6.3 拦截器骨架（自己写，这里只给结构）

```
preHandle：
  ① 从注解/配置取该接口的阈值与窗口（见第七节）
     没有配置 → 不限流，return true（放行所有未标注的接口，避免误伤）
  ② 组装标识：userId 优先，取不到则用 IP
  ③ 调 RateLimitService.tryAcquire(key, window, limit)
  ④ 返回 false（超限）→ 必须自己写响应体（见 6.4），return false
  ⑤ 放行 → return true
```

### 6.4 ⚠️ 返回 false 必须自己写响应体

`preHandle` 返 false **只是告诉 Spring"别往下走了"**，它不会生成任何响应内容 —— 不写就是**前端收到内容为空的 HTTP 200**（`JwtInterceptor.writeUnauthorized` 的注释里已经踩过这个坑）。

**限流的响应要和 401/503 明确区分开**：

| 情况 | 业务码 | 前端该做什么 |
| --- | --- | --- |
| token 无效/过期/登出 | **401** | 刷新 token，换不到就**跳登录页** |
| Redis 挂了（黑名单查不了） | **503** | 提示重试，**保留 token、不跳登录页** |
| **请求太频繁** | **429** | 提示"操作过于频繁，请稍后再试"，**不跳登录页、不清 token** |
| 请求成功 | 200 | — |

**为什么 429 不能复用 401**：401 的语义是"你的凭证有问题"，前端会**清 token 跳登录页**。如果限流也返 401，用户被限流一次就被踢下线、还得重新登录 —— 体验上是"系统坏了"。**这和 fail-closed 那条"503 不能写成 401"是同一个道理：用正确的信号报告失败。**

### 6.5 建议的响应头（可选但值得加）

```
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1758000120        ← 窗口重置的绝对时间戳（秒）
Retry-After: 37                      ← 还有多少秒可以重试
```

前端据此能显示"还需等待 37 秒"，而不是一个模糊的"操作太频繁"。**`Retry-After` 是 HTTP 标准头**，写上更专业。

## 七、阈值与配置

### 7.1 怎么配：注解 vs 配置文件

| 方式 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| **自定义注解**（`@RateLimit(limit=5, window=60)`）标在 Controller 方法上 | 一眼看出哪个接口有保护、阈值多少；能按接口差异化 | 需要写注解 + 拦截器里读 `HandlerMethod` | ⭐ **推荐**：直观、可讲 |
| 配置文件（`application.yml` 里按路径配） | 不用改代码就能调阈值 | 路径字符串容易写错；改配置要重启 | 阈值调优阶段再用 |

**注解需要的东西**（拦截器里怎么拿）：

```java
if (!(handler instanceof HandlerMethod)) return true;   // ★ 静态资源等要放行
HandlerMethod hm = (HandlerMethod) handler;
RateLimit rl = hm.getMethodAnnotation(RateLimit.class);
if (rl == null) return true;                            // 未标注 = 不限流
```

> `handler instanceof HandlerMethod` 这个判断**必须有**：不是所有请求都映射到 Controller 方法（静态资源、`/error` 转发等），直接强转会 `ClassCastException`。

### 7.2 本项目的建议阈值（**演示值，不是生产值**）

| 接口 | 维度 | 阈值 | 理由 |
| --- | --- | --- | --- |
| `POST /auth/login` | IP | 10 次 / 分钟 | 防撞库；正常人不会一分钟登 10 次 |
| `POST /auth/register` | IP | 5 次 / 分钟 | 防批量注册 |
| `POST /auth/refresh` | IP | 20 次 / 分钟 | 正常前端 30 分钟刷一次，20/分钟极宽松 |
| `POST /article`、`POST /comment` | userId | 10 次 / 分钟 | 防灌水 |
| `GET /article/list`、`GET /article/{id}` | IP | 120 次 / 分钟 | 正常翻页会连打，阈值要宽 |
| `GET /user/list` | userId | 30 次 / 分钟 | 管理类查询，收紧 |

**⚠️ 必须写进文档的一句話**：这些数字是**拍脑袋的演示值**。真实阈值要靠**流量观测**（打点统计 P99 QPS、按用户分布）来定 —— 面试时主动说这句，比背数字强。

## 八、降级策略：Redis 挂了怎么办（⭐ 本条最值钱）

### 8.1 限流是性能层 → **fail-open（放行）**

```java
try {
    return redis 脚本返回值 == 1;
} catch (Exception e) {
    log.warn("限流检查失败（Redis 不可用），放行本次请求", e);
    return true;      // ★ fail-open：放行
}
```

**理由**：限流的目的是"保护后端不被压垮"，而不是"证明请求合法"。Redis 一挂就**拒绝所有请求**，等于把一个**辅助组件**变成了**全站单点** —— 限流本身成了更大的故障。

### 8.2 与另外三处的对照（**一张表讲完整个降级体系**）

同一个项目、同一类 `try/catch`，**四个位置三种方向**：

| 位置 | 层次 | 依赖挂了 | 代码 | 为什么 |
| --- | --- | --- | --- | --- |
| `ArticleServiceImpl` 缓存（9 个 `cacheXxx` 封装） | **性能层** | **fail-open**：回源查 DB | `return null` | 缓存只是加速，挂了顶多慢 |
| `TokenServiceImpl.isRevoked` 黑名单 | **安全层** | **fail-closed**：拒绝，返 503 | `throw BusinessException(503)` | 查不到 ≠ 没被拉黑，放行 = 已登出的 token 复活 |
| `AuthorizationInterceptor` 读不到 `role` | **安全层** | **fail-closed**：拒绝，返 403 | `writeForbidden(...)` | 读不到角色说明请求没经过鉴权（可能被误加进放行名单），放行 = 权限校验被静默绕过 |
| **限流（本文档）** | **性能层** | **fail-open**：放行 | `return true` | 限流是保护资源，挂了不该把所有人挡在门外 |

**四个位置放进一条请求链上看**：`JWT（安全）→ 授权（安全）→ 限流（性能）→ Service（性能）`。**安全在前、性能在后**，各自的降级方向刚好和它们在链上的位置对应 —— 越靠近"判断请求合不合法"的越要 fail-closed，越靠近"优化体验"的越要 fail-open。

**面试话术**："降级方向取决于这层依赖的性质 —— 性能层失败要放行保可用，安全层失败要拒绝保安全。同一个 `try/catch`，方向正好相反。而且要看**失败的后果**：限流失败放行的后果是'可能被刷'，限流失败拒绝的后果是'全站不可用' —— 后者严重得多。**我们项目里这两种方向同时存在**：黑名单 fail-closed、缓存和限流 fail-open。"

> ⚠️ **别说成"所有 Redis 用法都 fail-open"**。同一个 Redis，在缓存/限流里是性能层（fail-open），在黑名单里是安全层（fail-closed）。**判断依据是"这个依赖坏了，放行会不会造成安全问题"，不是"用了哪个中间件"。**


### 8.3 但 fail-open 有个边界要写清

**❌ 不要无脑返回 true**。如果限流是为了防**正在发生的攻击**（比如撞库正在进行），Redis 挂时全放行等于把门敞开。更稳的做法是**降级到本地限流**（Guava `RateLimiter` 或 `Semaphore`，单机级），保住最低限度的保护 —— 但引入本地限流会带来"集群各节点额度不一致"的新问题。**本项目的取舍：fail-open + 日志告警，不做本地兜底**，理由是没有生产流量、集群部署也不在本项目范围内。**这个取舍要写在文档里**（知道边界在哪，比假装没有边界强）。

## 九、验收清单

### 9.1 限流本身

```
① 用脚本在同一分钟内打 POST /auth/login 第 1~10 次  → 前 9 次 code != 429，第 10 次起 code=429
② 等窗口过去（约 60 秒）再打                        → 恢复正常
③ 换一个 IP / 换一个账号打                          → 不受影响（额度是按维度隔离的）
④ 响应体文案 + X-RateLimit-* / Retry-After 头是否正确
⑤ 【关键】超限时 HTTP 状态码仍是 200，业务码是 429（不能直返 HTTP 429）
```

### 9.2 维度与顺序（⭐ 三个拦截器的顺序是本节的判据）

```
① 已登录用户打写接口 → 命中 userId 维度（换 token 但同一 userId，额度应继续累加）
② 未登录打 /auth/login → 命中 IP 维度
③ 【关键】把限流拦截器调到 JwtInterceptor 之前
     → 观察业务接口是否退化成 IP 限流（userId 维度失效）
     → 验证完把顺序改回来（这是最容易在重构中改错的地方）
④ 【关键】把限流拦截器调到 AuthorizationInterceptor 之前
     → 用普通用户 token 狂打 GET /user/list（预期 403）
     → 观察该用户的限流计数是否被这些"注定 403 的请求"消耗掉
       有消耗 = 顺序错了（没权限的请求不该占额度）
⑤ 【顺带】三个拦截器同时存在时，确认 /auth/login：
     - 不走 JWT（放行）
     - 不走授权（无 @RequireRole）
     - 【必须走限流】← 最容易漏，因为前两个拦截器都排除了它
```

**④ 是这次新增的关键判据**：它验证的是"限流只拦合法请求"这个设计意图，而不是"能不能限住"。**功能测试通常只测 ①②，会漏掉 ④。**


### 9.3 降级（fail-open）

```
① 停掉 Redis（或把 spring.redis.port 改成 9999）
② 打任意带限流的接口 → 【期望放行】，且日志里有"限流检查失败，放行"
③ 【反例】若返回 429 或 500 → 说明写成了 fail-closed，限流把全站挡死了
④ 恢复 Redis，确认限流重新生效
```

### 9.4 回归

限流拦截器注册在 `/**`，**影响所有接口**。改完必须回归全量 16 个接口（用户 4 + 文章 5 + 分类 4 + 评论 3），确认**没被误伤**（尤其注意别把翻页请求打成 429）。

| 步 | 做什么 | 为什么这个顺序 |

| 3 | 写 `@RateLimit` 注解 + 在 2~3 个接口上试 | 先只标登录接口，影响面最小 |

## 十一、踩坑清单

| # | 坑 | 后果 | 避免 |
| --- | --- | --- | --- |
| 1 | 限流拦截器注册在 `JwtInterceptor` **之前** | 拿不到 `userId`，退化成 IP 限流 | 保证注册顺序，或用 `.order()` 显式指定 |
| 1b | ⭐ 限流拦截器注册在 `AuthorizationInterceptor` **之前** | **没权限的请求也消耗限流额度**。攻击者可用"注定 403 的请求"消耗目标用户/IP 的额度 → 廉价 DoS 放大器 | 顺序：`JWT → 授权 → 限流`；**限流只拦合法请求** |
| 2 | 限流也 `excludePathPatterns("/auth/**")` | **登录/注册被排除在限流外**（最该保护的接口反而没保护）。注意 ①② 都排除了它，**copy 过来就错** | 限流拦截器**只排除 `/error`** |
| 3 | 限流内也用 401 | 用户被限流即被踢下线跳登录页 | 用独立的 **429** |
| 4 | `preHandle` 返 false 不写响应体 | 前端收到内容为空的 HTTP 200 | 照抄 `writeUnauthorized` / `writeForbidden` 的写法 |
| 5 | **`INCR` 之后忘了 `EXPIRE`** | 计数器只增不减 → **该用户/IP 被永久限流**（第一次踩会以为是"限流太严"） | `INCR` 返回 1 时才设 `EXPIRE`；或用 Lua 一次做完 |
| 6 | 固定窗口跨越边界 | 实际通过量可达阈值 2 倍 | 知道这个缺陷；要精确就上滑动窗口 |
| 7 | **`ZCARD` + `ZADD` 分成两条命令** | 并发下放行超过阈值（check-then-act 竞态） | 打包进 **Lua** |
| 8 | Lua 里用 `redis.call('TIME')` | 时间点取决于脚本执行时机、脚本无法脱机测试 | 时间由 **Java 端传入**，且必须是 **`System.currentTimeMillis()` 长整型**（见下条） |
| 8b | ⭐ **把 `LocalDateTime`/对象当脚本参数传** | **所有 `@RateLimit` 接口 500**（含登录/注册）。症状像"认证坏了"，根因在限流层 | 只传 `String`/数值；**判据：Redis 里一个限流 key 都没有 = 脚本从未执行** |
| 9 | **`X-Forwarded-For` 直接采信** | 攻击者伪造该头即可**绕过限流** | 只在可信网关后才采信；本地直连用 `getRemoteAddr()` |
| 10 | `handler` 直接强转 `HandlerMethod` | 静态资源等请求抛 `ClassCastException` | 先 `instanceof` 判断 |
| 11 | ⭐ **ZSET 的 member 直接用时间戳** | member 重复是**覆盖**不是新增 → 同毫秒请求被合并 → **计数偏少、限流不触发**（阈值 5 时打 8 次可能全放行）。**且因为恰好卡在阈值上，很难发现** | member 用 `now .. '-' .. math.random(1000000)`，**score 保持纯时间戳**（用于按窗口清理） |
| 11b | `remaining <= 0` 当超限判断 | 返的是"放行**前**剩多少" → `limit=5` 实际放行 **6** 个（off-by-one） | 先判 `count >= limit` 再 `ZADD`；返回值用 `limit - count - 1`（放行后剩余） |
| 12 | 限流 key 没设 TTL | 冷 key 永久占用 Redis 内存 | Lua 里 `PEXPIRE` |
| 13 | 阈值拍脑袋定太紧 | 正常用户被挡（尤其移动端重试） | 从流量观测定；先宽后紧 |
| 14 | 以为限流能防住攻击 | 限流只减少损害，不阻止访问 | 真正的防线：鉴权 + 密码强度 + 失败锁定 |
| 15 | 限流 key 里不带接口路径 | 登录限 5 次/分钟会把用户访问文章的次数一起算进去 | key 必须含接口标识 + 维度标识（见 4.1） |
| 15b | **签名收了 `uri` 参数却没拼进 key** | `/article/1`、`/article/2` 共用同一个计数器 → 刷爆一篇会让其他文章打不开。**列表接口看不出来，只有详情接口才暴露** | key 拼装写在一个方法里，别让调用方自己拼 |
| 16 | 用 `Result.unauthorized` / `Result.forbidden` 写限流响应 | 限流被前端当成"凭证无效/无权限"，行为错乱 | 用 **429**（`Result.build(429, ...)` 或新增 `tooManyRequests`） |

## 十二、面试怎么答

| 问题 | 答案要点 |
| --- | --- |
| **为什么要限流？** | 保护后端资源不被单点打垮：防刷、防撞库、防爬虫。**注意它只减少损害，不替代鉴权** |
| ⭐ **固定窗口有什么问题？** | **临界双倍**：窗口边界两侧各打满一次，实际通过量可达阈值 2 倍。解法是滑动窗口或令牌桶 |
| **滑动窗口怎么实现？** | Redis ZSET 存请求时间戳：`ZREMRANGEBYSCORE` 清窗口外 → `ZCARD` 计数 → `ZADD` 记录。**三步必须放 Lua 里原子执行**，否则 check-then-act 竞态会让放行量超标 |
| **令牌桶和滑动窗口区别？** | 令牌桶**允许突发**（桶里攒的令牌可一次用掉），滑动窗口是硬性"过去 N 秒最多 M 次"。按场景选 |
| **限流放哪一层？** | 网关（Nginx/Spring Cloud Gateway）做粗粒度全局限流，应用层做**业务维度**（按 userId、按接口）。本项目在应用层用拦截器 + 注解 |
| ⭐ **Redis 挂了限流怎么办？** | **fail-open 放行**。限流是性能层，Redis 挂了就拒绝所有请求 = 把辅助组件变成全站单点。**但边界要清楚**：正在被攻击时 fail-open 等于开门，所以要有日志告警，必要时降级到本地限流 |
| ⭐ **你的降级策略是什么？** | **分四处讲**：缓存 fail-open、黑名单 fail-closed、**授权读不到角色 fail-closed**、限流 fail-open。**方向取决于依赖的性质（性能层 vs 安全层）+ 失败后果的严重性**，不是取决于"用了哪个中间件" —— 同一个 Redis，在缓存里 fail-open、在黑名单里 fail-closed |
| **三个拦截器的顺序怎么排？** | `JWT（你是谁）→ 授权（你能不能干）→ 限流（最后才决定让不让你干）`。**限流放最后**是因为：① 拿不到 `userId` 就只能按 IP 限；② **没权限的请求不该消耗限流额度**，否则攻击者能用"注定 403 的请求"消耗别人的额度（廉价 DoS 放大器） |
| **限流应该拦什么请求？** | **只拦合法请求**。非法的（token 无效、无权限）在更前面的拦截器就被拒了，不该占限流资源。这也是"安全在前、性能在后"的体现 |
| **限流怎么防绕过？** | **标识必须不可伪造**：userId 来自签名 JWT（可信）、IP 来自 TCP 连接（可信）、`X-Forwarded-For` 来自客户端（**不可信，只在可信网关后采信**） |
| **限流 key 会不会撑爆 Redis？** | 不会，但**必须设 TTL**（固定窗口用 `EXPIRE`，滑动窗口用 `PEXPIRE`），且滑动窗口的内存是固定窗口的数倍，阈值高时要评估 |
| **分布式限流和单机限流区别？** | 单机（Guava `RateLimiter`）额度是**每台机器各一份**，集群下总额度 = 机器数 × 阈值；Redis 集中式才是全局准确，代价是每次请求多一次网络往返 + Redis 成为依赖 |
| **限流阈值怎么定？** | 从**真实流量观测**来（按接口 QPS、按用户分布、P99），先宽后紧，且要能动态调整。拍脑袋定太紧会误伤正常用户 |

## 十四、实现记录（实测）

> 记实际踩到的坑、和本文档预判不一样的地方、以及阈值调优的观察 —— 这是面试素材的直接来源。

**状态：已实现并实测通过**（2026-09-18 晚）。

### 14.1 落地形态（与设计稿的差异）

| 项 | 设计稿 | 实际实现 |
| --- | --- | --- |
| 限流标识 | `learning:limit:{维度}:{标识}:{uri}` | 一致 ✅（`CacheKeys.rateLimit(dimension, group, uri)`） |
| 脚本调用 | `execute(script, keys, now, limit, window)` | 一致，但 `now` 必须是 **`System.currentTimeMillis()` 的长整型**，见 14.2 ① |
| 客户端 IP | `IpUtils` 取 | ✅，且 `IpUtils` 做成了 `@Component` + 实例方法，与 `JwtUtils` 风格统一 |

### 14.2 ⭐ 两个只有实测才能暴露的缺陷

**① `LocalDateTime.now()` 传给 Lua → 所有 `@RateLimit` 接口 500（含登录）**

```java
// ❌ 脚本第 3 行是 tonumber(ARGV[1])，传对象会在参数序列化阶段就抛异常
stringRedisTemplate.execute(script, keys, LocalDateTime.now(), limit, window);
// ✅ 传毫秒时间戳（和 window 的单位 1000*60 对齐）
long now = System.currentTimeMillis();
stringRedisTemplate.execute(script, keys, String.valueOf(now), String.valueOf(limit), String.valueOf(window));
```

**症状的误导性**：表现为**登录/注册/刷新全部 500**，看起来像"认证坏了"，实际是限流拦在中间挂了。
**关键判据**：`redis-cli KEYS "learning:limit*"` **一个 key 都没有** —— 说明**脚本从未执行**，问题在"调用脚本"而不是"脚本逻辑"。**只看接口返回会查错方向。**

**② ZSET 的 member 也用时间戳 → 同毫秒请求互相覆盖，限流不触发**

```lua
-- ❌ member 和 score 都是 now：ZSET 的 member 重复是【覆盖】不是新增
redis.call('ZADD', KEYS[1], now, now)
-- ✅ member 加随机后缀，score 保持纯时间戳
local member = now .. '-' .. math.random(1000000)
redis.call('ZADD', KEYS[1], now, member)
```

**实测证据**（阈值 5/分钟，连打 8 次全部放行）：

```
ZRANGE WITHSCORES:
1789736611860  1789736611860   ← 同一时间戳出现两次
...
ZCARD = 5                        ← 打了 8 次只记了 5 条（5 个不同毫秒）
```

**为什么这个 bug 特别阴**：它**恰好卡在阈值上**才没暴露 —— `ZCARD` 到了 5，而判断是"放行前剩多少"（`5-5=0` 时第 5 个请求仍放行），于是 8 次全部通过。**限流看起来在工作、只是阈值不精确**，比完全不工作更难发现。

**顺带修的 off-by-one**：原脚本返回"放行**前**还剩多少"，导致 `limit=5` 实际放行 6 个。改成返回"放行**后**还剩多少"（`limit - count - 1`）。

### 14.4 降级路径实测（2026-09-18，把 `spring.redis.port` 改成 9999 制造 Redis 不可达）

**六处 Redis 依赖逐一实测**，这就是 §8.2 那张表从"设计"变成"实测数据"的过程：

| # | Redis 操作 | 层次 | 期望 | 实测 | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 1 | 缓存（detail/views） | 性能 | fail-open | 放行（回源查 DB） | — |
| 2 | **限流**（本文档） | 性能 | **fail-open** | **register ×7 全部 200，无 429 无 500** | — |
| 3 | 黑名单读（`isRevoked`） | 安全 | fail-closed 503 | **503「认证服务暂时不可用」** | 2052ms |
| 4 | 黑名单写（`logout`） | 安全 | fail-closed 503 | **503** | 4038ms |
| 5 | refresh key 写（`issue`） | 认证 | fail-closed 503 | **503「服务暂时不可用」** | 5060ms |
| 6 | refresh key 读（`refresh`） | 认证 | fail-closed 503 | **503** | 4037ms |
| 7 | refresh key 删（`logout`） | 认证 | **fail-open** | 记日志、登出继续返回 | — |

**⭐ 最值得记的一条结论：超时时间决定故障时的"伤害半径"。**

实测每次失败的 Redis 往返 ≈ **2 秒**（配的 `spring.redis.timeout: 3000ms`）：

```
不碰 Redis 的路径（无 token 直接 401）    25 ms  ← 快速拒绝
读一次 Redis 失败                       2052 ms
删 + 写各失败一次（logout）              4038 ms
限流 + 写 refresh 各失败一次（login）     5060 ms
```

**所以 fail-closed 的代价不只是"拒绝请求"，而是"每个请求都等满超时"。** 一次请求里可能撞多次超时（login 要过限流 + 写 refresh → 5 秒）。

> **生产启示**：`spring.redis.timeout` 必须设短（几百毫秒级）。否则 Redis 抖动期间**所有接口被拖慢 2~5 秒**，Tomcat 线程被占住 → 连接池耗尽 → **从"部分功能不可用"升级为"整站雪崩"**。这比直接报错更伤。
>
> **面试话术**："降级策略决定可用性，**超时时间决定故障时的伤害半径**。fail-closed 是必须的，但配套必须有短超时，否则安全控制会把整个服务拖死。"

**另一个实测细节**：`refresh` 用**类型不匹配**的 token 请求，走的是 `isRefreshToken` 校验（不碰 Redis），**2029ms** —— 慢是因为限流拦截器先执行失败了。这说明**故障时每个请求都在为同一件事反复付超时代价**，进一步说明短超时的重要性。
