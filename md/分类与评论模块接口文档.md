## 二、表结构（已在 MySQL 中建好，本次无需建表）

> **2026-09-19 核对**：下面两张表的 DDL 已用 `SHOW CREATE TABLE` 与库里实际结构对齐（补上 `deleted` 列、评论表改为复合索引）。
> 早期的"命名提醒"（说 `文章模块接口文档.md` 里表名没有 `tb_` 前缀）**已失效** —— 那份文档已一并改正，四张表现统一 `tb_` 前缀。

### tb_category（分类表）

```sql
CREATE TABLE `tb_category` (
  `id`      bigint      NOT NULL AUTO_INCREMENT COMMENT '主键',
  `name`    varchar(50) NOT NULL COMMENT '分类名',
  `deleted` tinyint     NOT NULL DEFAULT '0' COMMENT '逻辑删除 0=正常 1=已删',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_name` (`name`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='分类表';
```

### tb_comment（评论表）

```sql
CREATE TABLE `tb_comment` (
  `id`          bigint       NOT NULL AUTO_INCREMENT COMMENT '主键',
  `article_id`  bigint       NOT NULL COMMENT '文章id',
  `user_id`     bigint       NOT NULL COMMENT '评论人id',
  `content`     varchar(500) NOT NULL COMMENT '评论内容',
  `create_time` datetime     DEFAULT NULL COMMENT '创建时间',
  `deleted`     tinyint      NOT NULL DEFAULT '0' COMMENT '逻辑删除 0=正常 1=已删',
  PRIMARY KEY (`id`),
  KEY `idx_article_create` (`article_id`,`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='评论表';
```

> ⚠️ **`idx_article_create` 是复合索引，不是早期的单列 `idx_article_id`。** 查询是 `WHERE article_id = ? ORDER BY create_time DESC`，**等值列在前 + 排序列在后**能让过滤和排序一次扫描完成（`EXPLAIN` 的 `Extra` 从 `Using filesort` 变成 `Backward index scan`）。单列 `idx_article_id` 已被复合索引的最左前缀完全覆盖，**已 `DROP` 掉**。索引设计详见 `文章模块接口文档.md` 第二节。

### 4. 删除分类（决策已定）

```
DELETE /category/{id}
Authorization: Bearer {{token}}
```

**权限**：**仅管理员**（`@RequireRole(1)`）—— 分类是**全站资产**，不属于任何用户，
所以只能靠角色校验（归属校验对它无意义）。这是**纵向越权**防护。

**成功响应**：

```json
{ "code": 200, "message": "操作成功", "data": null }
```

#### 三个方案与最终决策

`tb_article.category_id` 可空、**且没有物理外键**（项目约定，见知识库第 7 条）。所以数据库**不会**阻止你删掉一个下面还有文章的分类 —— 删完之后，那些文章的 `category_id` 就变成**悬空引用**（指向一个不存在的分类）。

三个方案：

| 方案 | 行为 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. 拒绝删除** | 若有文章引用 → 400「该分类下还有 N 篇**有效**文章，无法删除」 | 最安全，绝不产生悬空引用 | 用户需先手动清空 |
| B. 置空后删除 | 先把相关文章 `category_id` 置 NULL，再删分类 | 操作顺畅 | 文章变成"未分类"，且在用户没要求的情况下**悄悄改动了他的数据** |
| C. 级联删除 | 连文章一起删 | — | **数据丢失，不可接受** |

> **✅ 最终决策：方案 A（拒绝删除）**，且**保持现状不再改动**（2026-09-19 确认）。
>
> 理由：分类对文章是**弱引用** —— 不该因为分类消失就丢文章（排除 C），
> 也不该在用户没要求的情况下悄悄改动他的文章（排除 B）。
>
> **实现的实现细节**：计数用 `articleMapper.selectCount(eq(categoryId, id))`，
> 它受 `@TableLogic` 影响 → **自动排除已逻辑删除的文章**，所以"还有 N 篇"里的 N 只算**有效**文章。
> 提示语也因此明确为「N 篇**有效**文章」。
>
> **一个语义边界**：把某分类下**最后一篇**文章删掉后，就能删掉这个分类了 ——
> 这是符合预期的（那篇文章已逻辑删除，不再是"有效引用"）。

**错误场景**：

| 场景 | code | message |
| --- | --- | --- |
| id 不存在（或已逻辑删除） | 404 | 分类不存在 |
| 分类下有**有效**文章 | 400 | 该分类下还有 N 篇有效文章，无法删除 |
| 普通用户调用 | 403 | 无权限！ |

```
Content-Type: application/json
```

**请求体**：

```json

```

| 字段 | 类型 | 必填 | 校验 |
| --- | --- | --- | --- |
| articleId | number | 是 | 非空，且对应文章必须存在 |
| content | string | 是 | 非空，长度 1~500 |

**成功响应**：

```json
{ "code": 200, "message": "操作成功", "data": { "id": 5 } }
```

**错误场景**：

| 场景 | code | message |
| --- | --- | --- |
| articleId 为空 | 400 | 文章id不能为空 |
| content 为空 | 400 | 评论内容不能为空 |
| content 超 500 字 | 400 | 评论内容不能超过 500 字 |
| articleId 不存在 | 404 | 文章不存在 |

#### 两个要点

1. **必须校验文章存在**。因为没有外键，数据库不会拦你，不校验就会产生"评论挂在不存在的文章上"的脏数据：
   ```java
   if (articleMapper.selectById(dto.getArticleId()) == null)
       throw new BusinessException(404, "文章不存在");
   ```
2. **`user_id` 从 `@RequestAttribute("userId")` 取，不要从请求体读**。否则任何人都能冒充别人发评论（越权）。这和文章模块 `addArticle` 的做法一致。

**`create_time` 由后端设置 `LocalDateTime.now()`** —— 表里是 `DEFAULT NULL`，不手动设就是 NULL（与 `Article` 的做法保持一致）。

## 五、关键实现点

### 1. DuplicateKeyException 的文案曾硬编码（已修复）

**现状**（`GlobalExceptionHandler.java` 第 30~34 行）：

```java
@ExceptionHandler(value = DuplicateKeyException.class)
public Result<?> handleDuplicateKey(DuplicateKeyException e) {
    log.warn(e.getMessage(), e);
    return Result.paramError("用户名已存在！");   // ← 写死了
}
```

现在没问题（全库只有 `tb_user` 有唯一约束）。但 `tb_category.name` 上有 `uk_name`，**一旦你实现"新增分类"，添加重名分类就会返回"用户名已存在！"** —— 一个分类操作回了句用户名的事，必现。

**正确做法：Service 层先查后插，主动抛业务异常**

```java
// 新增时
Long count = categoryMapper.selectCount(
    new LambdaQueryWrapper<Category>().eq(Category::getName, dto.getName()));
if (count > 0) {
    throw new BusinessException(400, "分类名已存在");
}

// 改名时要排除自己
Long count = categoryMapper.selectCount(
    new LambdaQueryWrapper<Category>()
        .eq(Category::getName, dto.getName())
        .ne(Category::getId, id));
if (count > 0) {
    throw new BusinessException(400, "分类名已存在");
}
```

这样正常路径文案准确；**数据库的唯一索引仍作为并发兜底** —— 两个请求同时通过校验时，DB 会拦住第二个，不会写进两条重名数据。

同时把 handler 里那句文案改掉（改成"数据已存在"之类的中性说法），至少不要再误报"用户名"。

### 2. 评论列表怎么查作者昵称 —— 直接复用文章模块的技巧

照抄 `ArticleServiceImpl` 第 77~88 行的模式：

```java
// 1. 分页查出这一页的评论
IPage<Comment> result = commentMapper.selectPage(page, wrapper);

// 2. 收集本页所有 user_id 并去重
List<Long> userIds = result.getRecords().stream()
        .map(Comment::getUserId).distinct().toList();

// 3. 一次批量查回昵称，装进 Map
Map<Long, String> nicknameMap = userIds.isEmpty() ? new HashMap<>()
        : userMapper.selectBatchIds(userIds).stream()
            .collect(Collectors.toMap(User::getId,
                u -> u.getNickname() != null ? u.getNickname() : "默认昵称",
                (oldVal, newVal) -> oldVal));

// 4. 组装 VO
vo.setAuthorNickname(nicknameMap.getOrDefault(comment.getUserId(), "未知作者"));
```

**为什么不能循环里查**：10 条评论 = 10 次 SQL，这就是 N+1。用批量查之后总查询次数固定为 **2 次**（分页 1 次 + 批量 1 次），与页大小无关。

⚠️ 两个易错点：`userIds.isEmpty()` 必须短路（`selectBatchIds` 传空集合有问题）；`toMap` 的**第三个参数合并函数不能省**，否则重复 key 抛 `IllegalStateException`。

### 3. 一条能消除 filesort 的复合索引（面试加分）

评论列表的查询本质是：

```sql
SELECT ... FROM tb_comment WHERE article_id = ? ORDER BY create_time DESC LIMIT ?, ?
```

现在只有单列索引 `idx_article_id` → MySQL 先用它**过滤**，再把结果**重新排序**，`EXPLAIN` 的 `Extra` 会出现 `Using filesort`。

```sql
ALTER TABLE tb_comment ADD INDEX idx_article_create (article_id, create_time);
```

`article_id` 相同的那段在 B+ 树里本身就按 `create_time` 有序，**过滤 + 排序一次索引扫描完成**，`Using filesort` 消失。

**今天要做的事**：
1. 加索引**前**先跑一次 `EXPLAIN`，截图/复制结果
2. 执行 `ALTER TABLE`
3. 再加索引**后**跑一次 `EXPLAIN`
4. 把两次结果都贴进本文档（对比 `type`、`key`、`Extra` 三列）

> 你 2026-08-25 刚系统学过「索引失效 8 大场景 + EXPLAIN 实战」，这是第一次用在**自己项目的真实表**上。

### 4. 关于"平铺评论"

`tb_comment` **没有 `parent_id`**，所以本次只做**平铺评论**，不支持回复/盖楼。这是 2026-09-13 建表时就定下的设计（见 `文章模块接口文档.md`），不是遗漏。

若将来要支持盖楼：

```sql
ALTER TABLE tb_comment ADD COLUMN parent_id BIGINT NOT NULL DEFAULT 0 COMMENT '父评论id，0=顶级';
```

列表**仍返回扁平结构 + `parentId` 字段**，由前端按 `parentId` 组装成树 —— 后端不做嵌套，否则分页语义会被破坏。

## 八、跨模块行为约定（2026-09-19 确定）

本项目**不建物理外键**，所以"删除的连带影响"**只能靠应用层决定**，就必须显式约定。
这类决策散落在对话里会失传，集中记在这里：

| 关系 | 决策 | 具体行为 |
| --- | --- | --- |
| **分类 → 文章** | **拒绝删除** | 分类下有**有效文章**时不允许删分类，返回具体篇数（第 4 节，方案 A） |
| **文章 → 评论** | ⭐ **不级联** | 文章逻辑删除后，它的评论**仍是 `deleted = 0`** 留在表里。<br>访问 `GET /comment/list?articleId={已删文章}` 返 **404**（评论列表接口**先校验文章存在**，见第 6 节） |
| **用户 → 评论** | **不级联** | 用户逻辑删除后，他的评论仍在；列表里查不到作者 → 昵称兜底成 `"未知"` |
| **用户 → 文章** | **不级联** | 同上，文章保留，昵称兜底成 `"未知作者"` |

### 为什么选"不级联"

这些数据是**回收站思路** —— 误删时可以恢复（直接改 `deleted` 字段），一旦级联就不可逆了。

**代价必须一起写下来**（不是缺陷，是知情的选择）：

- 数据会堆积（表越来越大），需要靠归档策略而非级联删除来解决；
- **"评论查不到但实际存在"对排查者不直观** —— 查库能看到评论，走接口却是 404。
  排查时要知道：**评论接口的 404 可能是文章状态导致的，不一定是评论本身不存在**。

> **如果将来要改成级联**：删除文章时同时
> `commentMapper.update(null, wrapper.eq(articleId).set(deleted, 1))`，
> 并且**必须加 `@Transactional`** —— 项目里当前跨表写操作还没有事务注解，
> 这是引入级联时要一并处理的问题（跨表写必须保证"要么都成功"）。

### 评论列表的 404 判定（容易误以为"过滤条件失效"）

```
GET /comment/list?articleId={id}
  ① articleMapper.selectById(articleId) == null ?  → 404「文章不存在」
  ② 否则按 articleId 分页查评论
```

**第 ① 步受 `@TableLogic` 影响** → 文章逻辑删除后 `selectById` 返 null → 评论列表**直接 404**，
不会返回"空数组"。这个设计让"文章已删"这个状态**对前端显式可见**，而不是静默返回空列表。
